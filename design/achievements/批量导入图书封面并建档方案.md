## 1. 背景与问题

用户持有一批图书封面图片，希望批量导入系统并为图书建档。核心诉求：

1. 不想逐本手工录入；
2. 希望尽可能自动化——给图，系统自己搞定书名、作者、封面、入库；
3. 对识别可靠性有顾虑，希望有评估机制保证不产生脏数据。

本项目当前状态（经代码核验）：

- **后端 API 已就绪**：`POST /books/intake` 支持 `image + title + author` 入库，自动查元数据、落盘封面、查重去重；
- **无批量导入功能**：CLI 只有单本 `add`，前端无上传 UI；
- **无移动端代码**：全项目零 `.kt/.swift/.gradle`；
- **无 eval 机制**：无 golden set / benchmark 目录。

## 2. 三条候选路径对比与取舍

针对"批量录入图片并建档"，讨论过三条路径：

| 维度 | ① Agent + CLI（项目既有方向） | ② Android APK | ③ IM bot（飞书发图） |
|---|---|---|---|
| 后端改动 | **零**（API 全就绪） | 零，但多一个客户端要维护 | 新建 webhook 路由 |
| 新工程量 | 一个脚本 + eval | **全新 Android 工程**：相机、权限、HTTP、认证、UI、打包、签名 | bot adapter + vision 集成 |
| vision 识别书名 | 复用 Claude Code 视觉（现成） | APK 内集成 ML Kit OCR / 云 vision | 调外部 LLM vision |
| 能否批量 | 能，扫目录循环 | 最自然——连续拍照、相册多选 | 一张一张发，批量体验差 |
| 与项目架构契合度 | 设计方案 2.2/2.3 明确分层：Skill→CLI→API | 架构外挂，平行技术线 | 设计方案 2.3 即此流程图 |
| 维护成本 | 低（Python，同语言） | **高**（Kotlin/Gradle，与 Python+Vue 栈异构） | 中 |
| 最快能跑起来 | 后端起来 + token 设好，立刻 | 起步数天～一周 | 需飞书机器人配置 |

### 2.1 否决 APK 的理由

1. **项目栈是 Python 后端 + Vue 前端，零移动端代码。** 引入 APK 等于开第二条技术战线，与现有 CLI/Agent/Skills 体系完全平行，长期维护两个客户端。
2. **设计方案自己给了答案。** `design/achievements/家庭图书管理系统-设计方案.md` 2.3 节"一次典型交互"画的流程是：飞书发图 → Agent 多模态识别 → CLI → API。技术选型表"图像/书封识别"明确写"Agent 多模态（首选）+ 可选 PaddleOCR 兜底"——设计者把视觉识别交给 Agent，未规划原生 APP。
3. **APK 唯一真实赢面是"手机连续拍照 + 相册多选"交互。** 但为这一个交互点付出整套 Android 工程代价，对家庭量级（几十到几百本，一次性导入为主）不划算。该交互需求可由 PWA + 前端上传页在现有栈内满足。

### 2.2 最终选定：路径 ①（Agent + CLI）

分工：

- **Agent（Claude Code，本会话）**：用视觉能力逐张读封面图，提取书名、作者；
- **后端**：拿 title 查元数据 + 落盘封面 + 查重入库（已有，零改动）；
- **桥梁**：复用 `cli/bookshelf/client.py` 的 `BookshelfClient.add()`，认证/超时/查重全继承。

## 3. 选定方案的完整链路

```
用户：把封面图放进某个目录（如 ./covers）
用户：告诉 Agent "这是封面目录"
   │
   ▼ Agent: Glob 扫出全部图片
   ▼ Agent: 逐张 Read（看封面）→ 读出书名、作者
   ▼ Agent: 生成清单 batch_manifest.json 让用户核对（防识别错误）
用户：核对/修正清单
   │
   ▼ 脚本: 读清单，逐本调 POST /books/intake
   ▼ 后端: 查元数据 + 落盘封面 + 查重入库（intake.py 全自动）
   │
   ▼ Agent: 汇总报告（成功 / 已存在跳过 / 失败及原因）
```

### 3.1 关键设计点

**为什么中间要"生成清单让你核对"这一步？**

不是可选的。vision 识别在艺术字、竖排、外文书、模糊倾斜图上会失分。正确做法是：

- 第一遍：Agent 识别 → 出清单 → 用户核对（这一遍顺便构成 eval 的金标准集）；
- 后续：若 eval 显示准确率达标（书级完全正确率 ≥ 75%），后续批次可跳过核对直接自动入库；不达标则保持逐批确认。

这样把 `book-intake/SKILL.md:108-109` 的约束"识别结果存疑时先确认再 add"从主观判断变成基于指标的自动阈值开关。

**为什么用 ISBN 文件名是 CLI 方案的退路，不是首选？**

用户原始诉求是"连书带封面一起导入"，封面是正面图，**正面通常没有条码**（条码在封底）。现有"扫码识别 ISBN"那条路（`recognize_isbn_from_image`）对正面封面图无效。所以首选让 Agent 用 vision 读书名，而非依赖文件名 ISBN。ISBN 文件名仅作为"用户恰好有 ISBN"时的快捷匹配键退路。

**为什么 Agent 走 REST API 而非 IM webhook？**

项目 Agent 接入架构是"主动发现 + 主动调用"模式，非 IM webhook：

- 发现面：`/agent/manifest.json`、`/agent/openapi.json`、`/.well-known/api-catalog`、`/agent/skills/index.json`；
- 认证：Owner 在 `/agent-access/*` 注册 client → 建 grant（scope `books:write`）→ 签发 token，Agent 用 `Authorization: Bearer {token}` 调用；
- Skills 分发：`/agent/skills/index.json` + 可下载 bundle。

当前无 webhook 通道（`backend/app/api` 下无 webhook 路由，grep 仅命中测试文件）。

### 3.2 复用的现有代码构件（零新后端代码）

| 构件 | 位置 | 作用 |

| `BookshelfClient.add()` | `cli/bookshelf/client.py:152` | 已封装 multipart 上传 + Bearer 认证 + 90s 超时，批量脚本直接调 |

## 4. 可靠性保障：eval 机制设计

vision 识别是 Agent 端的事（后端不集成 LLM），无 eval 就无法回答"能否信它批量入库"。项目当前零 eval 机制，需从零建，但可贴合项目既有"命中率量化"意识（`design/discussions/ISBN元数据API调研.md` 已用"覆盖率 ~98%""命中率 ~50-60% → ~80-90%"评估数据源）。

### 4.1 评什么——指标设计照入库主键优先级

入库主键逻辑：ISBN > 书名 + 作者。eval 指标照此优先级：

| 指标 | 为什么重要 | 合格线（建议） |
|---|---|---|
| ISBN 识别率 | 最强主键，识别对了后端全自动 | 能读到才评，不强制（正面通常没条码） |
| **书名准确率** | 无 ISBN 时的主匹配键，错了会建脏数据或查重失败 | **≥ 90%** |
| **作者准确率** | 同名书消歧用，错了影响小但不该错 | **≥ 80%** |
| **书级完全正确率** | 书名+作者都对的比例，代表"能直接入库不干预"的比例 | **≥ 75%** |

**字段级 vs 书级必须分开报。** 若作者准确率明显低于书名，说明 vision 读作者名有系统性问题（外文作者名、笔名），batch 脚本要对作者字段加一道确认。

### 4.2 金标准集设计

`tests/eval/covers/` + `tests/eval/golden.json`：

```json
[
  {"file": "三体.jpg", "expected": {"title": "三体", "author": "刘慈欣", "isbn": null}, "difficulty": "normal"},
  {"file": "坚如磐石.jpg", "expected": {"title": "坚如磐石", "author": "孙颙", "isbn": null}, "difficulty": "art_font"},
  {"file": "sapiens.jpg", "expected": {"title": "Sapiens", "author": "Yuval Noah Harari", "isbn": null}, "difficulty": "foreign"},
  {"file": "blurry.jpg", "expected": {"title": "...", "author": "...", "isbn": null}, "difficulty": "blurry"}
]
```

**难度分档是 eval 有意义的前提**——否则 90% 准确率是无用数字（可能全是简单样本）。分档：

| 档位 | 特征 | 预期 |
|---|---|---|
| `normal` | 清晰中文横排书名 | 主要得分来源 |
| `art_font` | 艺术字/变形字体 | **最大失分点** |
| `vertical` | 竖排书名（日台书、部分文学书） | 中等失分 |
| `foreign` | 外文书 | 中等失分 |
| `blurry/angle` | 模糊、倾斜、反光（真实拍照条件） | 真实场景失分 |

每档 8-10 张，总量 30-50 张即统计显著。**这批图就是用户真实的书——本来就要导入，顺手标注即金标准，零额外采集成本。**

### 4.3 评估脚本

`scripts/eval_cover_recognition.py`，复用批量脚本 dry-run 模式——只 vision 识别、不调 API 入库：

```
对 golden.json 每条：
  Read(file) → vision 识别 → 输出 {predicted_title, predicted_author}
  和 expected 对比 → 记录命中/miss
输出：总指标 + 分档指标 + miss 清单（哪本错了、错成什么样）
```

结果写 `tests/eval/results-{date}.json`，关键指标同步进 `task-list.md`。

### 4.4 阈值与回归接入项目机制

| 改变 | 重跑 eval |
|---|---|
| 换 vision 模型（Claude → GPT-4V） | 必跑，对比指标 |
| 改识别 prompt（加"注意竖排"等指令） | 必跑 |
| 升级 Claude 版本 | 跑 |
| 批量入库前 | 跑一次确认当前基线 |

**触发逻辑**：eval 书级完全正确率 < 75% → batch 脚本强制走"逐本人工确认"模式，不允许自动入库；≥ 75% 才开放自动批量。把 `SKILL.md:109`"识别结果存疑时先确认"从主观判断变成自动阈值开关。

## 6. 实施顺序（推荐）

批量导入与 eval 是同一件事的两面——用户本就要核对识别结果，把核对结果结构化存下来即金标准，重跑即回归测试，几乎无额外成本。故串行推进：

1. **建金标准**：用户把要导的封面图放进 `tests/eval/covers/`，Agent 逐张 vision 识别 → 用户核对纠正 → 结果直接成 golden set（一次劳动，两个用途：既导了书，又建了 eval）；
2. **跑首次 eval**：拿 golden 算基线指标，看当前 vision 在真实书单上的准确率；
3. **指标达标 → 开放批量自动入库**；不达标 → 脚本走逐本确认模式，分析 miss 集中档位，针对性改 prompt 后重跑；
4. **以后任何变量变更**（换模型/改 prompt/升级版本），重跑 eval 防回归。

## 7. 扩展路径（未来可选，非本期）

若未来"手机拍照"成刚需，性价比排序：

1. **前端加"批量上传"页面**：Vue 已有，加 `FormData` 多选上传，比 APK 省 10 倍工作量。当前前端连上传 UI 都没有，这是真缺口；
2. **PWA**：参考 Audiobookshelf 同类系统 Web/PWA 路线（调研报告 3.5 节），复用现有 Vue 前端，加 manifest.json + Service Worker 即可"装"到手机桌面；
3. **原生 APK**：仅当 PWA 无法满足时才考虑，需评估是否值得开第二条技术线。

IM bot（路径 ③）作为设计方案 2.3 的原始设想，可在 Agent + CLI 跑通后作为交互层叠加，但需新建 webhook 通道，本期不做。
