## 1. P1 · BUG-288：异常文本仍泄露编码后的密钥

定位：`backend/app/services/metadata/http.py:68-71`。

复现输入：`https://example.invalid/books?api_key=synthetic%2Bsecret%2F2026%3D&q=isbn`。模拟 `URLError` 的异常文本回显该原始 URL，调用真实 `get_json` 并捕获诊断事件。

实际事件中的 `url` 已是 `api_key=***`，但 `error` 仍包含 `api_key=synthetic%2Bsecret%2F2026%3D`。该编码值可还原为完整虚构密钥 `synthetic+secret/2026=`。

原因：`parse_qsl` 先解码为 `synthetic+secret/2026=`，`_error_message` 只替换这个解码值，未匹配异常中的原始百分号编码写法。现有测试只使用没有编码字符的 `secret123`。

原查询参数 URL 脱敏已有效；异常回显的 URL 与敏感值也需要覆盖编码形态，不能只替换解码值。

## 2. P2 · BUG-289：租约未过期时点击恢复，任务变失败且恢复入口消失

定位：`backend/app/services/intake_workflow.py:907-914`；`frontend/src/views/BatchIntakeView.vue:419-432`。

复现：任务与命令均 executing，原执行进程已经中断，持久化租约还剩 30 秒 → 立即点击“恢复执行”。

实际结果：执行器按设计跳过未过期租约，命令仍 executing；汇总却因为完成数为 0 把任务改成 failed。前端只在 confirmed/executing 状态提供执行/恢复入口，回执的重试按钮也只处理 failed 命令。因此刷新后既无恢复按钮，也无该命令的重试按钮；租约随后过期不会自动修正任务状态。需要额外 API 调用才能恢复。

应在仍有 executing 命令时保留可恢复的状态或入口。现有前端恢复测试只证明首个按钮可点击，服务端响应和刷新后的状态由独立 mock 提供，没有覆盖租约尚未到期的完整流程。

## 3. P2 · BUG-286：拆分后的已保存人工候选仍被重识别清空

定位：`backend/app/services/intake_workflow.py:302`；拆分创建新版本 1 的位置为 528-531 行。

普通工作台可达的操作顺序：两张照片组成一个候选 → 保存人工修正书名/作者，版本变为 2 → 拆出第二张照片，新候选版本为 1，但继承人工字段与 `evidence.source=user` → 再识别，照片识别返回 timeout。

实际结果：原候选版本 3 的人工字段保留；拆出候选被删除并换成空白候选。复现输出：

```text
拆分前后人工字段：原候选 v3 / 拆出候选 v1，二者 title.source 均为 user
重识别后：原候选 title=人工修正书名，photo_ids=[p1]
重识别后：替换候选 title=None，photo_ids=[p2]
```

仅以 `version > 1` 识别人工输入不充分。直接由手工构建接口保存的 source=user、version=1 候选也有同样问题。已保存的人工来源应参与保护判断，或者拆分继承保护标记。现有保护回归没有拆分步骤。

## 4. P2 · BUG-285：确认与重建并发时，同一照片仍可建立两本书

定位：`backend/app/services/intake_workflow.py:293-305`。

两个真实数据库会话交错：

1. 会话 A 开始重建，读取已确认/已执行照片集合为空。
2. 会话 B 确认原候选甲（引用 p1）并提交。
3. 会话 A 使用旧归属集合继续重建，创建候选丙，也引用 p1；已确认甲被保留。
4. 确认丙并执行整批。

实际结果：任务返回 completed，真实领域服务建立《并发书甲》和《并发书丙》两个不同 book_id；两个完成回执的 photo_ids 都是 `[p1]`。已用数据库会话交错和真实书目创建验证。

串行重建过滤已确认照片的修复有效，但归属检查和重建之间缺少原子保护。确认与重建应在同一任务内互斥或具备提交时的归属复验。现有回归只覆盖确认完成后再开始重建。
