# BUG-302：存量 SQLite 库前向迁移修复

日期：2026-10-08。范围为已经执行旧版位置迁移、`shelf_photos` 尚无 `AUTOINCREMENT` 的数据库。此前新库修复不等于存量库已经升级。

## 根因与复现

Alembic 按 revision 记录已执行的迁移。修改 `l3c4d5e6f7a8` 的建表代码，并重新执行 `upgrade head`，不会重新创建旧照片表。旧表删除最大 ID 后仍可能复用 ID，照片 version 又从 1 开始；迟到的旧删除请求可能误删新照片。

新回归复制现有迁移到临时目录，移除 l3 中的 AUTOINCREMENT 参数模拟原结构，执行原 l3 后再恢复修订版文件，验证正常 `upgrade head` 的效果。不依赖 Git，也不改真实数据库。

修复前，四个关键验收场景失败：旧表缺少 AUTOINCREMENT；照片表删空后，即使保留回执、仅保留审计或同时保留两者，升级后新上传仍复用旧 ID。

## 实现

新增前向迁移 [m4d5e6f7a8b9](../../backend/alembic/versions/m4d5e6f7a8b9_shelf_photo_autoincrement.py)，接在 l3 后：

- 对旧 SQLite 表使用 Alembic batch 重建，启用 AUTOINCREMENT，保留照片行、字段、外键和索引。
- 恢复现存照片 ID、已有 sqlite_sequence、照片幂等回执和照片审计中的最大 ID。写回 sqlite_sequence，使已删除照片的编号也不再分配。
- 已带 AUTOINCREMENT 的表不重建，已有高水位不降低；空表且无历史记录时从初始序列开始。
- PostgreSQL 不改表；降回当前修订版 l3 保留防复用属性，避免回退安全保护。
- 迁移不改变照片路径、回执、审计或图片文件，不修复此前已经发生的误删。历史上界来自仍保留的记录；不会宣称能重建已经丢失的全部历史。

方案依据：[SQLite AUTOINCREMENT 与 sqlite_sequence](https://www.sqlite.org/autoinc.html)、[Alembic SQLite batch 迁移](https://alembic.sqlalchemy.org/en/latest/batch.html)。具体行为同时由项目当前安装版本的真实迁移测试验证。

## 验证

[test_bug302_existing_database_migration.py](../../backend/tests/test_bug302_existing_database_migration.py) 共六个场景通过：

1. 旧库升级保留完整照片行和文件，保留索引／外键及主图约束；删除再上传 ID 递增，迟到删除拒绝且新照片仍在。
2. 照片表删空，仅保留幂等回执的库升级后不复用旧 ID。
3. 照片表删空，仅保留审计的库升级后不复用旧 ID。
4. 同时保留回执和审计的库升级后不复用旧 ID，历史记录不被改写。
5. 已带 AUTOINCREMENT 的库曾使用 700 后删空；重复升级与降回 l3 再升级后仍不降低序列，新照片 ID 大于 700。
6. PostgreSQL 离线迁移分支不执行 SQLite 序列或重建表操作。此项不等于真实 PostgreSQL 实机验收。

项目 `backend/.venv` 后端全量：**1091 passed、30 skipped、0 failed**，397.91 秒；六项专项通过。既有 `members.username` 表达式索引反射警告不涉及本迁移。迁移链检查确认唯一 head 为 `m4d5e6f7a8b9`；只读复核未发现阻断缺陷。

## 应用范围与发布

本轮只读核查本地 `backend/data/bookshelf.db` 仍在 k2，尚无照片表；没有升级这个真实库，也没有检查或修改 LWA 数据库。

修复代码进入运行环境后，按 [部署说明](../../docs/deployment.md) 备份并停止所有旧写入实例，再在后端运行目录、使用应用同一 Python 环境和 DATABASE_URL 执行 `python -m alembic upgrade head`。新库和旧 l3 库均走同一 head；无需手工改表或再次修改原 migration 文件。
