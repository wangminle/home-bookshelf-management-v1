## 仍未收口的 7 项

### BUG-261 / P1：成功响应解码失败和已提交后的 502 仍会自动重发

定位：`cli/bookshelf/client.py:83-105`、`:107-122`；`scripts/batch_import_covers.py:458-472`。

`DecodingError` 未进入 `ApiOutcomeUnknownError`，会落入宽泛 `HTTPError` 分支，被包装为“无法连接 API”；502 非 JSON 则被包装为普通 `RuntimeError`。批量脚本据此标记 `failed`，随后 `--retry-failed` 重发。5xx 不能证明写请求未提交，现有新增测试中“502 确定未成功”的假设不成立。

两个复现分别为：

- `test_damaged_encoded_success_is_not_retried`：返回损坏 gzip 的 HTTP 201，首次保存 `failed/network_error`，重跑产生第二次 POST；应为结果未知，暂停自动重试。
- `test_gateway_error_after_commit_does_not_duplicate_purchase`：MockTransport 内执行真实 `intake_book` 并提交书目、副本、购买，再返回 502。首次标记 `failed`，`--retry-failed` 后临时库实测 **2 条购买记录、2 个副本**，图书去重没有保护附加写入。

需要按写请求的提交确定性分类：响应解码错误和无法证明未提交的服务端/网关失败进入结果未知；只有可证明未送达或明确业务拒绝的请求才进入安全重试路径。回归必须检查实际副本/购买条数，不能只断言异常类型。

### BUG-260 / P1：推断出的确认资格没有持久化

定位：`scripts/batch_import_covers.py:425-435`。

兼容旧清单时，`status=confirmed` 且 `confirmed_fields=[]` 会推断出 title/authors 等确认字段，但只保存到局部变量。首次请求明确失败后清单写回 `status=failed`，`confirmed_fields` 仍为 `[]`。下一次 `--retry-failed` 不再传 `prefer_confirmed` 或确认字段。该情形同时影响新 scan 骨架中用户只修改状态的使用方式。

`test_inferred_confirmation_survives_first_failure` 实测：首次参数为 `prefer_confirmed + [title, authors]`，失败清单确认字段为空，重试参数丢失两者。现有新回归直接以“failed 且已有 confirmed_fields”作为起点，没有经过首次推断及失败落盘。

需要在首次执行及可能改写运行状态之前，把推断资格写回清单并持久保存；覆盖完整 confirmed→失败/未知→核对后重试流程。

### BUG-254 / P1：过期租约恢复会把 ISBN 冲突直接恢复成成功

定位：`backend/app/services/intake_workflow.py:967-989`。

恢复通过 `_find_existing_book` 查重，只要找到对象就直接补 `completed` 回执，没有执行 ISBN 归属校验或核对人工解决决策。普通创建/关联路径已经增加的冲突阻断不覆盖这里。

`test_expired_recovery_preserves_isbn_conflict_guard`：库内为《活着》/余华，候选为《三体》/刘慈欣配《活着》ISBN；没有预览、没有 force_link。预置命令在执行中崩溃并租约到期后重试，结果为 `completed`、绑定《活着》、`warnings=[]`，候选变成 `executed`。

查重命中不等于该命令已成功提交。恢复需要绑定可核验的命令执行证据，且不能绕过 ISBN 冲突及人工解决条件。

### BUG-252 / P1：过期租约恢复只检查版本，没有检查参数摘要

定位：`backend/app/services/intake_workflow.py:961-970`。

正常领取后的 `_bind_snapshot_or_fail` 检查版本和摘要；恢复分支只检查 `candidate_version`。`preview_matches` 可以修改 `match_book_id` 而不增加候选版本，因此存在版本相同、摘要已变化的合法操作路径。

`test_expired_recovery_checks_parameter_digest`：确认创建命令后，再预览命中既有书，目标 ID 发生变化；重算参数摘要与命令摘要不同。过期恢复仍返回 `completed`，没有返回 `stale_confirmation`。

恢复必须与正常执行采用同一套版本、参数摘要及资源校验，不能在补回执前提前返回成功。

### BUG-253 / P1：旧恢复快照仍可清除新执行者的有效租约

定位：`backend/app/services/intake_workflow.py:1002-1015`。

`_mark_stale_failed` 的 UPDATE 仅限制执行 ID 和 `status=executing`，不限制原 lease_owner、lease_epoch 或过期时间。两个 Session 中，一个持有旧的过期执行快照，另一个原子领取新租约后，旧 Session 的恢复仍能把新租约标为 failed 并清空。

`test_stale_recovery_does_not_clear_new_active_lease`：新 Session 成功领取 `new-active-worker` 且租约未到期；旧 Session 恢复时发现候选版本变化，最终数据库 `lease_owner=None`、`status=failed`，并发生额外领取。正常回执的 owner+epoch 条件化不能保护这个独立恢复写入分支。

所有恢复、失败标记和关联 ChangeSet 的状态更新都需要一致的租约归属条件，并依据 UPDATE 是否成功决定后续动作。

此外，`intake_book` 内部提交、业务副作用与回执非同事务，以及副本/购买恰好一次未覆盖，仍是原验收未满足的范围差距。本次发现实际租约错误，因此不能把 BUG-253 仅归为待范围变更。

### BUG-256 / P1：恢复回执提交绕过执行中撤权检查

定位：`backend/app/services/intake_workflow.py:765-770`、`:953-989`。

`run_command_execution` 在调用 `_assert_executor_authorized` 之前调用恢复；恢复成功即直接返回。恢复函数不接收 requester 身份，补回执提交时也没有刷新权限。

`test_expired_recovery_checks_authorization_at_commit`：进入恢复时 Owner 有效，查重过程中用另一 Session 停用 Owner；恢复仍提交 `completed` 回执并标记候选/ChangeSet 执行完成，未抛 `WorkflowAuthError`。API 入口鉴权只能证明进入请求时有效，不能替代恢复提交时的授权核验。

恢复应传递请求者身份，并在恢复状态写入前和提交前核验授权，与正常执行保持一致。

### BUG-263 / P2：重映射会漏计仍存活的原创建对象

定位：`scripts/batch_import_covers.py:655-666`。

原始 `book_id` 与最终 `final_book_id` 分开已修复；但净新增计算在两者不同的时候直接排除原 ID，且不查询其存活状态。清单关联重定向不会删除数据库对象，不能由“已重映射”推断“原创建不成立/已删除”。

`test_reconcile_counts_surviving_original_creation`：本批创建的 10 仍存活，照片显式改关联到既有 18；reconcile 实测仅核对 18、`net_created=0`。按规划 §4.4 的“本批创建且最终仍存活”口径应为 1，既有 18 本身不计新增。

净新增需要独立核对原始创建 ID 的存活状态；最终照片关联仍使用 final_book_id，两种口径分别计算。
