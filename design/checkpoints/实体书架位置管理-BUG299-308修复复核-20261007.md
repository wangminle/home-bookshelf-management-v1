## 2. 七项需要处理的问题

### R1［P1］补录失败后关闭再打开，原幂等键丢失（BUG-299）

定位：[CopyProvisionForm.vue](../../frontend/src/components/CopyProvisionForm.vue) 第 33～40 行；父页面 [BookDetailView.vue](../../frontend/src/views/BookDetailView.vue) 第 465～470 行。

同一组件内直接重试已正确复用 key。但 key 只保存在组件局部变量；响应丢失后，用户点击取消会通过父级 v-if 销毁组件，再打开同一书目的补录表单时重新生成 key。

独立探针通过真实 Vue DOM 操作失败→取消→重开→填写完全相同的册数／归属／位置，观测到两次 items 相同、key 不同。按 key 保留回执的 mock 后端累计建了 2 册；此册数是模型结果，不是访问真实库的结果。实际 [storage_intake.py](../../backend/app/services/storage_intake.py)／[storage_tx.py](../../backend/app/services/storage_tx.py) 的语义也以 key 区分新操作，第二个 key 不会命中首个回执。

建议将未确认结果的 key 与规范化载荷保存在跨表单生命周期的操作状态中；未核对结果前，取消／重开不能将同一次重试变为新的补录操作。单独存“最近一次 key”仍不能替代结果核对。

### R2［P2］启动恢复误删另一个实例正在上传的暂存文件（BUG-301）

定位：[storage_photos.py](../../backend/app/services/storage_photos.py) 第 481～495 行，上传前置写暂存在第 187～188 行。

恢复先读取一次 referenced 集合，再扫描文件；无引用的 .staged 立即删除。上传却在事务提交前写暂存文件，另一个 worker／实例启动恢复时，这个文件尚不在已提交引用中。

隔离实测在写暂存之后、begin_operation 之前调度另线程恢复：恢复 removed=1；原上传随后正常提交并返回照片回执，但 final、staged 均不存在，真实内容 API 返回 404。同 key 重试和再次启动恢复都不能修复。没有使用或删除任何真实照片。

建议通过可识别的上传所有权／租约或跨进程协调区分活跃上传与遗留暂存；不能根据一次引用快照立即删除所有无引用暂存。

### R3［P2］并发同键恢复上传，一个请求返回 500（BUG-301）

定位：[storage_photos.py](../../backend/app/services/storage_photos.py) 第 136～137 行；调用点第 256 行。

两个请求都看到原 staged 存在后，先到者 replace 成功，后到者 replace 抛 FileNotFoundError。重放分支未捕获该异常。用两个真实 TestClient、独立 Session 和文件检查点屏障实测，同 key 请求得到 HTTP 201、500；正式文件最终存在。

建议让转正操作可并发重入，竞争失败后重验 final：已被其他请求成功转正应视为恢复完成；真实文件系统失败应有明确恢复语义，不能突破幂等回执返回流程。

### R4［P2］清空选择与切换房间，没有失效旧详情请求（BUG-304）

定位：[PlacementTargetPicker.vue](../../frontend/src/components/PlacementTargetPicker.vue) 第 41～49、60～66 行。

两族 A→B 请求已受代际保护，但代际递增位于空值 return 后；切房间也未使旧书架详情请求失效。独立真实组件探针确认：清空书架后旧层重新显示；切房间 B 后旧 A 架层显示到 B 的选择器；清空房间后旧书架数组仍被写回。

这里已验证的是陈旧 UI／状态回填，没有声称已在真实后端完成错误位置写入。建议每次父级变化先使全部下游请求失效，包括清空分支，再发起新请求；响应还需核对其所属房间／书架。

### R5［P2］新路由加载失败后，旧架展示与新架写请求再次错位（BUG-306）

定位：[StorageShelfView.vue](../../frontend/src/views/StorageShelfView.vue) 第 135～139 行；照片上传使用 props.shelfId 在第 176 行。

成功导航已修复。失败路径没有清空旧 detail：先显示书架 11，再切 shelfId=22，新详情 GET 404 后，DOM 仍显示书架 11、上传表单仍可用，同时出现“书架22不可见”。从该界面提交文件，fetch 目标为 `/storage/shelves/22/photos`。

这是实际组件发出的写请求证据，上传响应由 mock 返回，没有对真实后端写照片。建议参数变化时清空或隔离旧详情，加载失败不恢复旧对象的可写界面；写操作需绑定经成功加载验证的资源 ID。

### R6［P2］409 刷新期间恢复编辑，晚到回填覆盖新草稿（BUG-305）

定位：[StorageView.vue](../../frontend/src/views/StorageView.vue) 第 124、138 行及第 180～183 行。

提交 409 后调用 loadAll().then(syncOpenForms)，但提交函数已经解除 busy。探针挂起刷新 GET，确认保存按钮恢复启用，通过 DOM 输入新的草稿，再放行刷新。表单 prop 被替换后，新草稿被改为服务端名称。

建议等待冲突刷新完成再恢复编辑，或跟踪草稿代际、仅同步版本与明确允许覆盖的字段；“已刷新”提示不能在刷新尚未完成时宣告完成。

### R7［P2］BUG-307 竞态回归假阳性（BUG-309，测试缺陷）

定位：[StorageShelfView.test.ts](../../frontend/src/views/__tests__/StorageShelfView.test.ts) 第 65～67 行；新测试第 313 行。

stubFetch 不 await handler，而新增测试返回 deferred Promise。Promise 被当同步 result 读取，body 为 undefined；之后 resolve 并不进入实际响应应用链。

独立变异验证只在 Vite 内存转换中移除 copiesReqId 响应、错误与 loading 守卫，没有改仓库代码：原“快速切换格子”回归仍 1 passed；正确等待响应的独立探针对当前代码通过，对同一变异失败并显示旧格书名。

BUG-307 的业务修复当前有效，问题在回归保护。需修正 handler 类型、await 响应，并保证 A 的晚到载荷真正走过 fetch.json 与界面赋值链。

台账同步：BUG-299、301、304、305、306 重新标为待修复；BUG-302、307 保留已修复并补适用前提／测试证据；新增 BUG-309 记录测试缺陷，CHK-134 记录本次复核。`task_list_cli check` 通过。

## 3. BUG-302 的迁移前提

修改原 migration 加 sqlite_autoincrement，对首次建库有效；已有原 revision 的数据库不会重跑 upgrade。隔离实验先用 `2b2767a` 原 migration 建库，再换补丁 migration 执行 upgrade head：sqlite_master 仍无 AUTOINCREMENT；删除 ID=1 后新照片仍为 1，迟到旧 version=1 删除成功且 remaining=[]。

当前本地 `backend/data/bookshelf.db` 仍在 `k2b3c4d5e6f7`，尚无 shelf_photos 表，本轮未发现该本地库受到旧 schema 影响。因此：

- 若“未发布迁移”意味着所有需要保留的数据库均未执行旧 revision，当前修法可以在这个前提下通过；应在发布前核查目标库。
- 若有已执行原 `l3c4d5e6f7a8` 的需保留库，必须增加前向迁移或同等升级处理，并在存量库验证 ID 不复用；不能把全新测试库的结果用作升级证据。

台账保留 BUG-302 已修复，并追加上述适用前提与未覆盖的升级边界，不宣称已经验证所有部署库。
