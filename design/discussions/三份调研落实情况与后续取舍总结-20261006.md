### 2.1 当前落实情况

| 查询超时与故障降级 | 已实现总 deadline、批次超时及 Provider 异常隔离；故障是否发生、为何返回空仍应结合诊断证据判断 |

| 纯 LLM/Scholar 替代 ISBN 数据库 | 未采用，符合原报告取舍；视觉识别已实现不代表“全部失败后由 LLM 联网搜索”的兜底也已实现 |
| 保护人工核对值，保留来源与冲突 | [intake.py](../../backend/app/services/intake.py) 的 `prefer_confirmed`、`confirmed_fields`、`matched_source` 和冲突警告已有实现；不等于每个入口都强制使用同一种确认策略 |
| 多源逐字段补全 | 尚未实现完整合并；当前查询链在命中后返回该 Provider 的结果 |
| 豆瓣、Hardcover、Wikidata、ISBNdb | 属于后续候选，没有必要为了完成调研清单全部接入 |

现行查询链设置 12 秒总 deadline、8 秒 Provider 批次上限。这些是控制返回等待的代码边界，不保证慢请求线程立即停止，也不保证每条入库在 12 秒内完成；领域写入和图片处理还有各自耗时。

### 2.2 尚待验证的假设与局限

1. 原报告中的中文命中率“50–60% → 80–90%”、NLC 覆盖约 98% 和 LLM 慢 10–100 倍，没有提供本项目统一样本、测试条件及统计方法。它们只能作为经验或研究假设，不能进入验收结论。
2. 数据源的理论覆盖与本机可用性是两件事。接口存在、插件可运行、库中有书，都不能证明当前部署能稳定取得正确版本和完整字段。
3. [RES-006 原始记录](../checkpoints/RES-006-metadata-diagnosis-20261002.json) 只有 2026-10-02 本机的五组探针：NLC 五次超时、Google Books 五次限流、OL 三次命中和两次无结果。它证明当时故障与空结果不能混同，不能代表长期服务水平或总体中文覆盖率。
4. 配置 API Key 是应用标识和配额管理的基础，不保证限流消失。Google 官方要求公共数据请求携带 Key 或 OAuth 标识；仍需检查实际项目配额和响应。[Google Books 官方说明](https://developers.google.com/books/docs/v1/using)
5. 旧调研偏重“选择哪个源”，没有充分验证逐字段正确率、版本/译本混淆、字段缺失、缓存与维护成本。社区插件的许可证也不能替代数据提供方条款、缓存及再分发边界的核验。

### 2.3 仍值得借鉴与后续取舍

最有价值的增量是按字段补空与来源追踪，而非继续堆叠 Provider。komf 官方实现允许在主结果缺字段时从其他来源补充，并按 Provider 限定字段；该模式值得做小规模对比实验。[komf 官方说明](https://github.com/Snd-R/komf#metadata-aggregation)

建议先确认书目身份，再在不覆盖人工确认值的前提下补出版社、简介、分类和封面；保留每个字段的来源、时间与冲突。不能用“响应最快”直接推导“结果最正确”，也不应为了增加字段完整度把不同版本的元数据拼在一起。

缓存、限流退避、错误分类和按健康状况切换也应纳入 Provider 运行策略。Open Library 官方要求尽量缓存、标识应用、遵守调用限制，批量获取另有使用约束，不能将免费理解为无限调用。[Open Library 使用规范](https://openlibrary.org/developers/api)

### 3.2 当时调研的局限

- **Star 筛选有偏差。** 高 Star 不等于中文藏书适配、维护成本低或家庭成员愿意使用，也可能遗漏小型中文实体书项目。
- **产品相似不能证明数据语义相同。** 阅读清单、电子书文件与家庭实体册数的用途不同；“已读”“拥有”“借阅”“存放位置”需要分别建模和验证。
- **差异化结论证据不足。** “这些项目没有 IM + 多模态入口”不能作为已经验证的独特性或用户价值。应测量少填了多少字段、减少了多少时间、误录和重复是否更少。
- **“OPDS 零成本扩大前端”过于乐观。** 还需目录实现、文件访问控制、阅读器兼容和维护，是否值得做取决于真实电子书使用需求。
- **外部实现会变化。** MyBibliotheca 当前官方说明使用 KuzuDB，并增加 Google Books 与扫码/导入改进。借鉴应固定版本，并比较运行约束，不应照搬早期技术栈概括。[MyBibliotheca 官方仓库](https://github.com/pickles4evaaaa/mybibliotheca)

### 3.3 仍值得借鉴与后续取舍

当前最贴近家庭需求的问题是：一本书有几册、谁拥有、放在哪里、是否重复购买，以及迁移和备份后能否恢复。已有书目不自动证明家里拥有一册，照片数也不是册数。

优先收口 PLN-013 的副本与位置语义，并沿用 [实体书架与位置管理设计](../plans/实体书架与图书位置管理-功能分析和设计-20261005.md) 中的人工册数确认思路。该文件仍是待评审设计，不代表相关功能已开发。OPDS 和在线阅读按电子书需求单独决定，不为对齐参考项目而提前实施。

### 4.2 两个重要区别

**拍照建档与已有书目整理不是同一个场景。** 前者从照片生成候选并创建/关联书目；后者从已有书目缺失字段出发，生成旧值/新值/来源可见的修订提案。前者可以验证确认、幂等和恢复模式，不能替后者完成 AN-0/AN-3 的价值与效果验收。

**Owner 工作流与 Agent Runtime 的授权主体不同。** 当前批量执行由 Owner Web 请求发起；未来 Agent 代表用户执行时，还需绑定 Client、Grant、版本、范围、限制与具体审批，不能借用 Owner 身份或复用 Cookie 来补齐架构。

### 4.3 当时调研的局限

这份报告已经区分事实、推论与建议，也明确了暂不引入组件和试点门禁，比早期两份更适合长期参考。但仍有以下边界：

1. 七层模型与对象清单完整，不代表本项目需要一次性建齐全部层和表。应优先服务真实业务切片，避免把架构完整度当交付目标。
2. 缺少本项目真实任务频率、人工处理基线、审批负担及净节省数据。报告中的 go/no-go 和基础设施升级阈值是试验规则或重新评估信号，尚不是经运行数据校准的生产结论。
3. 家庭与中小组织跨度较大；当前家庭身份和共享书目基础不能证明多组织、租户、空间和组织间共享已实现。
4. 外部资料包含 main/current/draft 链接，访问日期不能冻结内容；正式采用时仍需保存规范版本、Commit/Tag 与依赖锁定证据。
5. 单机 SQLite 自动化回归不等于跨进程、多写实例、PostgreSQL、跨日运行或外部副作用的完整恢复验收。

### 4.4 仍值得借鉴与后续取舍

优先从少量真实能力建立统一目录，例如搜索、详情、缺失字段检测和元数据预览，再用契约测试核对各入口的权限、风险、版本与输出。Home Assistant 当前官方设计按每次请求的上下文贡献工具，支持“领域拥有能力、授权决定暴露集合”的方向。[Home Assistant 官方设计](https://developers.home-assistant.io/docs/core/llm/)

维持轻量状态机和模块化单体；先补内部关联 ID 与业务执行证据，再决定是否需要外部 Trace、实时事件协议或工作流引擎。长期 Memory、私人笔记、自动写入和跨组织关系权限必须按专项基线分阶段评审，不能由“AI-native”标签自动扩权。
