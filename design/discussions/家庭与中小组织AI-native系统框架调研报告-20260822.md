## 0. 执行摘要

本次调研关注的不是“给传统系统增加一个聊天框”，也不只是“怎样让 Agent 安全调用 API”，而是一个更完整的问题：

> 当家庭或中小组织的内部系统同时服务人类和 Agent，并具有数据生成、消费、更新、审批、自动化和多端交互时，怎样设计一套足够 AI-native、同时不过度工程化的系统框架？

调研结论是：目前没有一项单独标准完整覆盖这类系统。业界正在形成的是一组分层组合：

- Home Assistant 一类领域系统提供稳定事实、Intent/Tool 和按上下文暴露的能力；
- MCP 规范 Agent 与工具、资源之间的协议；
- AG-UI 规范 Agent 与人机界面之间的事件和状态流；
- LangGraph、Temporal、OpenAI Agents SDK、n8n 等提供可暂停、可恢复、可审批的 Agent/Workflow 执行模式；
- Cedar、OpenFGA、OAuth RAR/Token Exchange 提供策略、关系、细粒度授权和委托语义；
- OpenTelemetry GenAI 与 OWASP Agentic/AISVS 提供运行追踪、安全风险和验证框架；
- Dify、Open WebUI 等展示了 AI 工作空间、知识、模型、工具和多用户产品形态，也暴露了通用插件执行面的安全代价。

这些方案的共同点不是“模型统治系统”，而是：

1. **确定性领域系统仍是事实源**：模型输出、对话和 Memory 不能替代业务数据库；
2. **业务能力是第一等对象**：每项能力具有稳定 Schema、权限、风险、幂等和审计契约；
3. **Human、Workflow、Agent 分工**：固定流程交给 Workflow，开放判断交给 Agent，高风险决定交给 Human；
4. **Agent 是独立主体**：可以拥有高于普通 Member 的自动化能力，但不等同于 Owner；
5. **读写风险分层**：读取、建议、预览、审批、执行、回滚是不同阶段；
6. **交互入口与业务内核解耦**：Web、Mobile、Chat、Voice、CLI、MCP 最终复用同一业务能力；
7. **运行状态可持久化**：长任务、人工审批和失败恢复不能只存在于模型上下文；
8. **默认可观测、可撤销、可解释**：每个 Agent Run、工具调用、授权来源和业务变更均可关联；
9. **渐进式自治**：先 Assistant，再 Copilot，最后才在明确边界内进入 Autopilot；
10. **模块化单体优先**：家庭和中小组织不需要为 AI-native 提前采用微服务、事件总线或外置策略平台。

对家庭图书管理系统而言，现有方向已经具备较强基础：领域数据、服务层、CLI/Skills、Web、Agent Client/Grant/Token、统一 AuthContext、Catalog Read Model、审计和限流已实现基础；MCP 薄适配和封面 Resource 只有默认关闭的实验实现，尚未通过正式发布门禁。真正缺少的是上层运行框架：Capability 目录、WorkItem、AgentRun、ChangeSet、具体业务决定、领域事件和自主等级。

因此建议保持现有 FastAPI + SQLAlchemy + SQLite 的模块化单体，不引入通用第三方 Agent 平台作为业务内核；先在现有服务层上建设领域专用的最小协作与运行切片，再由真实需求决定是否扩展。

## 1. 问题定义

### 1.1 什么是本报告所说的 AI-native

本报告中的 AI-native，不以是否使用大模型或是否存在 Chat UI 判断，而以系统是否原生满足以下条件判断：

- 人和 Agent 都能成为可识别、可授权、可审计的参与者；
- 业务能力能被 UI、Workflow 和 Agent 以稳定契约调用；
- Agent 可以围绕目标规划和组合能力，但不能绕过业务规则；
- 系统能表达任务、运行、步骤、提案、审批、结果和产物；
- 长任务和人工介入后能够恢复；
- 数据、权限、上下文、记忆和模型输出有明确边界；
- 同一业务可以从 Web、移动端、聊天、语音、定时任务或外部 Agent 发起；
- 自动化程度可以按风险逐步提升，而不是一次性放开。

因此，“AI-native”首先是一种业务与运行架构，其次才是模型、Prompt 或 Agent 框架选型。

### 1.2 家庭和中小组织的特殊约束

与互联网平台和大型企业相比，这类系统通常具有：

- 数据量较小，但数据类型完整且包含隐私；
- 用户少，角色结构简单，但真实归属关系重要；
- 本地或局域网部署较多，运维能力有限；
- 一个 Owner 或少量管理员承担最终责任；
- 自动化价值来自减少重复劳动，而非大规模吞吐；
- 可恢复、可解释和低维护成本往往比水平扩展更重要；
- 前端可能从 Web 扩展到移动端、IM、语音和 Agent Client；
- 需要兼容网络不稳定、模型供应商变化和本地模型能力差异。

这决定了本项目应优先采用模块化单体、数据库状态机、稳定 Capability 和轻量事件机制，而不是复制大型企业 AI 平台。

### 1.3 Human 与 Agent 的本质差异

Human 和 Agent 可以调用相同业务能力，但不能被视为相同信任主体：

| 维度 | Human | Agent |
| --- | --- | --- |
| 身份 | Owner/Member 登录身份 | 独立 Client/Grant/Token |
| 意图来源 | 人直接选择或输入 | 模型理解、规划或定时任务 |
| 错误特点 | 偶发误操作 | 可高速、重复、组合式放大错误 |
| 会话 | 浏览器或设备会话 | Run、Thread、Client 会话 |
| 权限 | Role 与资源归属 | Scope、Data Scope、Constraint 与 Grant |
| 审批 | 可直接承担责任 | 高风险动作需要 Human 决策 |
| 可解释性 | 操作者通常理解界面 | 必须展示实际工具、参数和影响范围 |

因此最佳实践不是建立两套业务系统，而是建立两条身份和交互路径，汇合到同一能力、策略和领域服务。

## 3. 业界参考架构与项目分析

### 3.1 Home Assistant：最接近家庭 AI-native 领域系统的参照

Home Assistant 的核心价值不在于它使用了 LLM，而在于它先拥有稳定的实体、设备、区域、服务、Intent、权限和事件模型，然后将其中一部分以 LLM API 暴露。

其官方 LLM API 有几个关键设计：

- LLM 通过 Tool/Intent 操作领域能力，而不是直接使用完整 REST/WebSocket API；
- 内置 Assist API 与内置会话 Agent 使用相同的“已暴露实体和能力”边界；
- Assist API 不提供管理操作；
- Tool 按每次请求的 `LLMContext` 组装，可以根据 Assistant、设备和上下文返回不同集合；
- 领域集成可以贡献自己的 Tool，能力代码仍由所属领域模块维护；
- 同一 LLM API 可以被会话 Agent 使用，也可以经 MCP 暴露。

2026 年的 LLM Tool Platform 架构决策进一步强调：Tool 应由所属 integration 注册，并在每次请求时根据上下文动态生成；Prompt 片段应与 Tool 一起维护，防止 Tool 集合变化后 Prompt 失真。

**架构推论：**

- 领域模块拥有业务能力；
- Agent 层不复制业务知识；
- 工具不是全局静态清单，而是经过上下文和授权过滤后的能力视图；
- 同一能力可投影到内置助手和 MCP，不需要两套实现。

**对本项目的适用性：高。** 家庭图书系统应由书目、阅读、笔记、购买等领域模块提供 Capability Provider；MCP、Skills、CLI 和未来内置助手消费这些能力。

参考：[Home Assistant LLM API](https://developers.home-assistant.io/docs/core/llm/)、[LLM Tool Platform 架构决策](https://github.com/home-assistant/architecture/discussions/1412)、[MCP Server 集成](https://github.com/home-assistant/home-assistant.io/blob/current/source/_integrations/mcp_server.markdown)。

### 3.2 Calibre-Web、Paperless-ngx、Immich 与 Audiobookshelf：小型自托管系统的身份和数据经验

旧调研中的四类项目仍有价值：

- Calibre-Web 表明匿名浏览应映射为受限访问策略，而不是绕过权限；
- Paperless-ngx 表明 Web Session 与 API Token 可以进入同一授权模型，但对象权限和数据过滤仍在服务端执行；
- Immich 的细粒度 API Key 演进体现机器凭证默认拒绝和逐能力授权；
- Audiobookshelf 表明家庭媒体系统仍需要独立成员身份和进度隔离。

**架构推论：** AI-native 不会消除传统业务系统的身份、归属和字段分层；相反，自动化会放大任何模糊边界。

**对本项目的适用性：高。** 现有 Anonymous、Owner、Member、Agent 分轨，以及 Public Catalog 与完整业务 API 分离的方向应继续保持。

参考：[Calibre-Web](https://github.com/janeczku/calibre-web)、[Paperless-ngx API](https://github.com/paperless-ngx/paperless-ngx/blob/dev/docs/api.md)、[Immich](https://github.com/immich-app/immich)、[Audiobookshelf](https://github.com/advplyr/audiobookshelf)。

### 3.3 MCP：Agent 到工具与数据的协议，不是业务架构

MCP 提供 Tool、Resource、Prompt、发现、传输和授权等协议能力。官方规范强调：

- Tool 是模型可选择调用的能力；
- 用户应能看到暴露给模型的工具，并能拒绝敏感调用；
- 工具发现可以因当前授权和 Scope 不同而变化；
- HTTP 授权应采用 OAuth 资源服务器语义、Protected Resource Metadata 和目标资源绑定；
- Token 必须为当前 MCP Resource 签发，禁止向下游透传收到的 Token。

**架构推论：** MCP 是外部 Agent 的协议适配层。Tool 名称和 Schema 可以是 MCP 契约，但业务权限、归属、事务和数据裁剪必须在 MCP 下面的业务层完成。

**对本项目的适用性：高。** 当前“薄型 MCP、精选工具、共享 AuthContext/Read Model/审计/限流”的设计符合这一边界。

参考：[MCP Tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/draft/server/tools.mdx)、[MCP Authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization)、[MCP Inspector](https://github.com/modelcontextprotocol/inspector)。

### 3.4 AG-UI：Agent 到人机界面的候选协议

AG-UI 是面向 Agent 与用户应用的双向事件协议，覆盖：

- Run 生命周期和流式输出；
- Tool Call 过程；
- Snapshot + Delta 状态同步；
- Interrupt、审批、编辑、重试和取消；
- Shared State；
- Agent Steering；
- 自定义事件和多 Agent 组合。

AG-UI 自身不提供身份和业务授权，宿主应用仍需负责会话、用户、权限和数据边界。

**架构推论：** Chat、审批工作台和 Agent 运行面板应围绕统一事件模型构建，而不是每个前端自行解析模型文本。不过协议接入应晚于内部 Run/Event 契约稳定。

**对本项目的适用性：中，后期。** 当前无需实现 AG-UI，但应预留 `run_started`、`tool_proposed`、`approval_required`、`tool_completed`、`run_completed` 等稳定领域事件。

参考：[AG-UI Overview](https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/introduction.mdx)、[AG-UI Events](https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/concepts/events.mdx)。

### 3.5 n8n：Agent、Workflow、Schedule 与跨渠道审批

n8n 将 Agent 作为可配置、可发布、可定时运行、可从不同渠道访问的对象。其 Human-in-the-loop 模式允许敏感工具暂停，向指定审批渠道展示实际工具和参数，再批准或拒绝。

这一案例特别说明：

- 发起任务的渠道和审批渠道可以不同；
- 审批应绑定实际工具参数，而不是模型对动作的自然语言转述；
- 固定 Workflow 与开放式 Agent 应并存；
- Agent 的 Session、工具使用和待审批状态需要可查看。

**对本项目的适用性：高，作为产品模式参考；低，作为必须引入的运行依赖。** 当前可在现有后端实现轻量状态机，不必部署 n8n。

参考：[n8n Agents](https://github.com/n8n-io/n8n-docs/blob/main/docs/build/build-and-manage-agents.md)、[Human-in-the-loop for Tools](https://github.com/n8n-io/n8n-docs/blob/main/docs/build/integrate-ai/ai-examples/human-in-the-loop-for-tools.md)。

### 3.6 LangGraph、Temporal 与 OpenAI Agents：持久运行和人工介入

三个项目共同展示了成熟 Agent Run 的基本要求：

- 执行状态可以 checkpoint 或序列化；
- 工具调用可以产生 interruption；
- 人类可以批准、拒绝或修改；
- 恢复时继续原运行，而不是重新提示模型从头猜测；
- 副作用必须与可重放步骤分离，避免恢复导致重复写入；
- 长时间等待和进程重启不应丢失审批状态。

LangGraph 提供图状态、checkpoint、durable execution 和 interrupt；Temporal 提供更强的工作流持久化、Signal 和跨进程恢复；OpenAI Agents SDK 提供将 RunState 序列化并在审批后恢复的轻量模式。

**架构推论：** Human-in-the-loop 不是弹窗，而是一套持久状态机；Agent 恢复能力依赖明确的 Run、Step、ToolCall 和幂等副作用。

**对本项目的适用性：模式高、组件低。** 先用 SQLite 表和领域状态机实现；当任务跨天、跨多个外部服务并出现复杂补偿时再评估专用框架。

参考：[LangGraph](https://github.com/langchain-ai/langgraph)、[Temporal AI Cookbook](https://github.com/temporalio/ai-cookbook)、[OpenAI Agents Human-in-the-loop](https://github.com/openai/openai-agents-python/blob/main/docs/human_in_the_loop.md)。

### 3.7 Dify：AI 工作空间和生命周期的产品参考

Dify 将模型、Prompt、Workflow、Agent、RAG、Tool、发布和可观测性组合在同一工作空间中，适合观察一个 AI 应用从配置到发布的生命周期。

值得借鉴的是：

- Agent/Workflow 是有版本和发布状态的配置对象；
- 知识摄取可以建成独立 Pipeline；
- 模型供应商与业务应用解耦；
- 运行和评估成为产品内能力。

不适合直接照搬的是：

- 将通用 AI 平台作为家庭图书业务事实源；
- 为少量结构化数据引入完整 RAG、Redis、插件守护进程和沙箱栈；
- 让平台工作流替代已有领域 Service。

**对本项目的适用性：中，主要参考工作空间与版本治理。**

参考：[Dify](https://github.com/langgenius/dify)、[Dify Knowledge Pipeline](https://github.com/langgenius/dify/discussions/26138)。

### 3.8 Open WebUI：通用工具平台的安全边界

Open WebUI 的官方安全说明明确指出，Workspace Tools 和 Functions 可以在服务器进程权限下执行 Python 代码，创建或导入工具的权限接近服务器 Shell 权限；因此默认只应向管理员开放，并允许完全关闭插件面。

它同时展示了一个正确模式：即使某模型附加了工具，当前用户没有对应工具权限时，该工具仍应从可用集合中被过滤。

**架构推论：** Tool 可见性必须同时受 Agent 配置和当前主体权限控制；“允许创建工具”和“允许调用工具”是不同且高风险的能力。

**对本项目的适用性：高，作为反面边界。** 不开放运行时上传任意 Python Tool，不允许普通 Member 创建服务器执行代码；业务 Capability 由受版本控制的项目代码提供。

参考：[Open WebUI Security](https://github.com/open-webui/open-webui/blob/main/docs/SECURITY.md)、[Open WebUI Tools](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)。

### 3.9 Cedar 与 OpenFGA：策略和关系模型

Cedar 将授权请求建模为 `principal/action/resource/context`，并专门讨论 Agent 代表用户操作时如何同时保留 Agent 和用户身份。OpenFGA 使用类型、关系和关系元组表达用户与资源之间的权限，并提供模型即代码和模型测试。

**架构推论：**

- Role 只是授权输入之一；
- Agent 与被代表成员应分别表达；
- 权限模型应版本化并有正反测试；
- 上下文约束和资源关系不宜塞进不断膨胀的 Scope 字符串。

**对本项目的适用性：建模高、组件低。** 当前继续使用本地 `permission_policy` 和数据库模型；出现多家庭、临时分享和复杂关系继承时再考虑 OpenFGA，出现大量动态上下文策略时再考虑 Cedar。

参考：[Cedar Authorization Context](https://docs.cedarpolicy.com/bestpractices/bp-using-the-context.html)、[Cedar Best Practices](https://docs.cedarpolicy.com/bestpractices/bp-overview.html)、[OpenFGA](https://github.com/openfga/openfga)、[OpenFGA Sample Stores](https://github.com/openfga/sample-stores)。

### 3.10 OAuth RAR 与 Token Exchange：细粒度申请和委托语义

OAuth Rich Authorization Requests 使用结构化 `authorization_details` 表达 actions、locations、datatypes 等细粒度需求，并允许资源所有者只批准请求的一部分。OAuth Token Exchange 使用 `sub` 与 `act` 区分被代表主体和当前行动者，并可以形成委托历史。

**架构推论：** 项目当前 Scope + Data Scope + Constraint，以及 Agent/acting-for-member 的分离方向，与标准演进路径一致。

**对本项目的适用性：语义高、协议实现后期。** 内部数据模型可以借鉴，但当前局域网试点不需要建设完整授权服务器。

参考：[RFC 9396 Rich Authorization Requests](https://www.rfc-editor.org/info/rfc9396/)、[RFC 8693 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693)。

### 3.11 OpenTelemetry GenAI：运行追踪的共同语言

OpenTelemetry 的 GenAI 语义约定覆盖模型调用、Agent、Workflow、Retrieval、Tool Execution 和 MCP，并提供 `gen_ai.agent.*`、`gen_ai.tool.*`、conversation、workflow 等字段。

相关 Agent 约定仍处于 Development，且 Prompt、工具参数和结果可能包含敏感信息。

**架构推论：** 业务审计与技术 Trace 应分开保存，通过 `request_id/run_id/tool_call_id` 关联；先采用稳定的内部字段，再映射 OpenTelemetry，而不是默认采集正文。

**对本项目的适用性：中。** 当前优先定义关联 ID、耗时、结果、错误和模型/工具版本；不默认记录 Prompt、私人笔记或完整 Tool 参数。

参考：[OpenTelemetry GenAI Semantic Conventions](https://github.com/open-telemetry/semantic-conventions-genai)、[Agent Spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)。

### 3.12 OWASP Agentic 与 AISVS：从风险清单到可验证控制

OWASP Agentic 资料关注目标劫持、工具误用、身份与权限滥用、供应链、记忆污染、级联失败和 Human-Agent 信任等问题；AISVS 将 AI 系统安全要求组织为可验证的分级控制。

**架构推论：** Prompt 不能承担安全边界；工具 Schema、最小权限、审批、隔离、来源、审计、撤销、异常暂停和回归测试必须在模型之外实现。

**对本项目的适用性：高。** 应建立面向家庭规模的安全回归清单，而不是部署企业级治理平台。

参考：[OWASP AISVS](https://github.com/OWASP/AISVS)、[OWASP Agentic Security Initiative](https://github.com/OWASP/www-project-top-10-for-large-language-model-applications/tree/main/initiatives/agent_security_initiative)。

### 3.13 Arazzo：多步 API Workflow 的机器可读描述

Arazzo 是 OpenAPI Initiative 制定的 Workflow 描述规范，可以引用 OpenAPI/AsyncAPI 操作，表达步骤、输入、输出、成功和失败动作。

**对本项目的适用性：低到中，后期。** 当 Agent Bootstrap 需要发现跨多个 REST 操作的稳定业务流程时可评估；当前使用 Capability 定义、OpenAPI operationId、Skills 和 MCP Tool 已足够。

参考：[Arazzo Specification](https://spec.openapis.org/arazzo/latest.html)。

## 4. 跨项目共同模式

### 4.1 领域事实与模型推理分离

模型负责理解、规划、生成候选和解释；数据库与领域服务负责事实、约束、事务和最终状态。模型输出必须经过 Schema 验证和业务命令处理。

### 4.2 Capability 代替“裸 API 暴露”

适合 Agent 的能力通常比 REST 端点更少、更稳定、更接近业务意图。例如应提供“预览元数据修订”，而不是让 Agent 自行组合任意 PATCH 字段。

### 4.3 Contextual Capability

Agent 能看到的工具集合取决于：

- 当前 Agent Client；
- Grant 和版本；
- Scope/Data Scope/Constraint；
- 当前用户或 acting-for-member；
- 部署模式；
- 功能开关；
- 工具发布状态和风险等级。

因此工具清单本身也是授权结果。

### 4.4 Workflow、Agent 与 Human 三分

| 类型 | 最适合的工作 |
| --- | --- |
| Workflow | 步骤确定、规则稳定、应可重复执行 |
| Agent | 需要理解、搜索、判断、动态选择能力 |
| Human | 目标澄清、价值判断、高风险批准和例外处理 |

调研样本共同支持“不把所有自动化都做成 Agent”的建议；它是本文的架构取舍，不是对所有成熟系统的普遍事实判断。

### 4.5 状态外置与可恢复执行

对话上下文不能成为唯一运行状态。任务、步骤、审批、工具结果、重试和最终产物必须有持久表示，才能在刷新页面、进程重启或等待数日后恢复。

### 4.6 建议与执行分离

高风险写入推荐采用：

```text
Observe -> Plan -> Preview -> ChangeSet -> Approve -> Re-authorize -> Execute -> Verify -> Audit
```

批准对象必须绑定实际参数、资源集合、版本和有效期，不能批准模型的模糊转述。

### 4.7 多端只是不同投影

Web 表单、移动端、Chat、Voice、CLI 和 MCP 可以拥有不同交互体验，但不应产生不同业务真相或权限实现。

### 4.8 渐进式自治

一个能力应经历：

1. 只读和解释；
2. 生成建议；
3. 人工确认后写入；
4. 限界自动执行；
5. 仅在评估和实际使用证明安全后扩大范围。

## 5. 推荐的家庭/中小组织 AI-native 参考框架

### 5.1 七层模型

| 层 | 核心职责 | 建议形态 |
| --- | --- | --- |
| 交互层 | Web、Mobile、Chat、Voice、CLI、MCP | 多适配器，不含业务真相 |
| 协作层 | WorkItem、Run、ChangeSet、Approval、Artifact | 数据库持久对象 |
| Agent Runtime | 理解、规划、Tool 选择、暂停恢复 | 轻量运行器，后期可替换 |
| Capability 层 | Query、Command、Workflow、Tool Schema | 领域模块注册和版本化 |
| Policy 层 | 身份、Scope、Data Scope、Constraint、归属 | 统一策略函数 |
| 领域内核 | 业务模型、事务、事件和事实 | 模块化单体 |
| 治理与运行层 | 审计、Trace、评估、限流、配置、回滚 | 横切能力 |

### 5.2 一等对象

建议至少具有以下概念，未必全部在首期建表：

- `CapabilityDefinition`：可被谁以何种方式调用的业务能力；
- `AgentProfile`：Agent 的用途、模型策略、允许能力和版本；
- `WorkItem`：人或系统希望完成的业务任务；
- `AgentRun`：Agent 对 WorkItem 的一次执行；
- `AgentStep`：模型、工具、等待或人工步骤；
- `ChangeSet`：拟议的结构化业务变更；
- `ApprovalRequest`/`Decision`：人类决策证据；
- `Artifact`：报告、导入清单或其他持久产物；
- `DomainEvent`：业务事实变化；
- `AutomationRule`：事件或时间到任务的映射；
- `MemoryItem`：经确认、带范围、来源和有效期的长期偏好。

### 5.3 三个平面

也可以从运行角度将七层模型归纳为三个平面：

- **Record Plane**：领域数据、权限、审计，是事实源；
- **Action Plane**：Capability、Workflow、Command 和事务；
- **Intelligence Plane**：Agent、模型、上下文、Memory 和评估。

Intelligence Plane 可以替换模型或框架，但不能破坏 Record Plane 和 Action Plane 的契约。

两种视图的映射如下：

| 七层视图 | 三平面主归属 | 说明 |
| --- | --- | --- |
| 交互层 | Intelligence/Action 的入口 | 不保存业务真相 |
| 协作层 | Record Plane | 保存任务、运行、提案和决定证据 |
| Agent Runtime | Intelligence Plane | 可替换的规划和运行组件 |
| Capability 层 | Action Plane | 稳定业务动作语言 |
| Policy 层 | Record/Action 横切 | 读取身份与授权事实，约束每次动作 |
| 领域内核 | Record + Action Plane | 业务事实、规则和事务 |
| 治理与运行层 | 三平面横切 | 审计、Trace、评估、限流和回滚证据 |

上述基础支持“无需重写领域系统”的建议，但不等于当前已经拥有完整 Agent Runtime 或已发布标准 MCP。

### 6.2 主要缺口

| 缺口 | 当前表现 | 影响 |
| --- | --- | --- |
| Capability 目录 | REST、CLI、Skills、MCP 各有清单，缺统一元数据 | 风险、权限和版本易漂移 |
| Agent Run | 外部 Agent 承担运行，服务端缺统一 Run 记录 | 难以暂停、恢复和解释 |
| WorkItem | 用户目标主要存在于会话或外部 Agent | 无统一任务状态与负责人 |
| ChangeSet | 写入多为直接命令 | 无标准预览、批准和回滚边界 |
| Approval | 已有 Grant 审批规划，缺具体业务动作审批 | 写工具难安全开放 |
| Artifact | 报告和导入结果多为即时响应 | 难以复查和复用 |
| Domain Event | 有操作日志但不是稳定事件契约 | 难以安全触发自动化 |
| Agent Eval | 有测试与 MCP 评估规划，缺版本化任务集 | 模型/Prompt/Tool 变更难比较 |
| Memory | 尚无正式模型 | 后续容易把聊天记录误当长期事实 |

### 6.3 两类授权与一类业务决策不能混同

- `GrantApproval`：决定 Agent 能获得什么能力，始终由 Owner 决策；
- `MemberConsent`：决定 Agent 是否可以处理某成员的 L3 数据，由受影响 Member 表达同意或拒绝，仍不能替代 Owner 批准 Grant；
- `ChangeSetDecision`：决定某个已经获授权 Agent 的具体业务提案是否执行，由 Capability 的审批策略决定。首个元数据整理试点固定为 Owner 决策；未来 Member 只能在明确规则下决定仅影响本人且不扩大 Grant 的低风险 ChangeSet。

三者是并列证据，不能相互替代。Agent 有效权限仍是 Grant、服务端能力上限、Data Scope、Constraint、资源归属、consent 和具体审批的合取结果。

### 6.4 现有设计中应继续坚持的边界

- Agent 是独立主体，不属于 `owner/member` 角色枚举；
- Member 最多申请，Owner 唯一批准 Agent Grant；
- Agent 能力可以超过 Member，但不能触碰 L4 管理与安全层；
- MCP 是薄适配，不直接访问 ORM；
- 匿名 Web 可见不等于匿名 MCP；
- 查询时过滤，不在响应后删除敏感字段；
- 个人笔记等 L3 数据不因“AI-native”自动进入 Agent 上下文；
- 写工具必须另行评审，不从只读能力自然升级。

## 7. 本项目建议

### 7.1 立即采用

1. 建立统一 Capability 定义及契约测试；
2. 给所有入口统一 `request_id`，给 Agent 路径增加 `run_id/tool_call_id`；
3. 定义 WorkItem、AgentRun、ChangeSet、Approval 的最小持久化切片；Artifact 和逐 Step 持久化按首个场景实际需要启用；
4. 将首个写场景设计为 Copilot，而不是 Autopilot；
5. 所有写命令支持幂等、乐观并发、影响上限和执行前重新授权；
6. 在三份规划基石中固定职责和冲突优先级；
7. 用现有 SQLite 和服务层实现任务租约、checkpoint、幂等、并发、超时和恢复，不增加外部基础设施。

### 7.2 使用验证后采用

1. 领域事件驱动的低风险自动化；
2. Agent Run 工作台和跨端审批通知；
3. 受控长期 Memory；
4. 内置 Assistant 和 AG-UI 投影；
5. 标准 MCP OAuth；
6. OpenTelemetry GenAI 映射；
7. Arazzo 工作流描述。

### 7.3 明确暂不采用

- 微服务拆分；
- Kafka 等外部事件总线；
- 外置 Cedar/OpenFGA 服务；
- Temporal 集群；
- Dify/n8n 作为业务内核；
- 通用插件市场和运行时 Python Tool 上传；
- 将全部结构化数据向量化；
- 默认长期保存完整 Prompt 与工具正文；
- 多 Agent 自主协商和 A2A；
- Agent 永久删除和安全管理权限。

## 8. 推荐的首个 AI-native 闭环

最适合验证框架的首个闭环不是私人笔记，也不是永久删除，而是“书目元数据整理”：

```text
Owner/Member 发起整理任务
  -> 建立 WorkItem
  -> Agent 读取共享书目和缺失字段
  -> 调用查重/元数据查询 Capability
  -> 生成 ChangeSet
  -> 展示逐书旧值、新值、来源和置信度
  -> Owner 批准、修改或拒绝
  -> 服务端重新授权并检查资源版本
  -> 执行领域 Command
  -> 验证结果并生成 Artifact
  -> 审计关联 WorkItem/Run/Grant/ChangeSet
```

选择它的理由：

- 数据主要位于家庭共享层；
- Agent 的搜索、匹配和判断能够产生明显价值；
- 变更可以预览；
- 可限制单批数量；
- 可记录来源和旧值；
- 不需要先开放私人笔记；
- 能同时验证 Capability、Run、ChangeSet、Approval、幂等和审计。

首个试点在 AN-0.6 形成并由 Owner 签署 `MetadataProviderProfile`，冻结：元数据 Provider/API/版本、条款与许可证证据、允许缓存和再分发范围、字段来源、单批上限、请求超时/重试、字段匹配优先级、冲突策略、置信度生成方式和评估样本；AN-3.1 只能按该 Profile 实现 Preview Capability。Profile 变化必须重新评审。置信度只用于排序和提示，不能代替 Human 批准。应用成功后保留 before snapshot 和逐项执行回执；若目标资源版本未再次变化，可以生成反向 ChangeSet，不能承诺对所有外部副作用自动回滚。

AN-0.7 先按 AI-native 总纲第 21.1 节做不依赖 Runtime 的商业可行性预门禁；AN-3 受限试点完成后，再按第 21.2 节评估样本量、人工基线、净节省、审批耗时、质量、安全和恢复。业务效率阈值可以在试验前留痕调整；越权、未批准写入、敏感泄露、错误静默覆盖、重复提交和失效授权继续生效等安全不变量始终为零容忍，不能通过风险接受调宽。

## 9. 采用门槛与架构升级信号

只有出现以下信号时才升级基础设施：

下列数值是“启动重新评估”的默认信号，不是自动采购或迁移决定；连续观察窗口默认 4 周，真实部署可在 AN-0 记录更合适的阈值。

| 候选组件 | 启动重新评估的默认量化信号 |
| --- | --- |
| LangGraph | 至少 3 个生产 Agent 流程都需要循环/分支/checkpoint/人工编辑状态，或自研 Runtime 为这些语义新增超过 500 行专用编排代码 |
| Temporal | 超过 10% Run 跨 24 小时，或同一流程包含至少 3 个需补偿的外部副作用，或恢复成功率连续两周低于 99% |
| OpenFGA | 出现至少 3 个家庭/组织间共享空间，或关系授权类型超过 10 种且每次改动都需修改应用代码 |
| Cedar | 授权决策需要组合至少 8 个上下文属性，或上下文策略变更每月超过 4 次并造成代码发布负担 |
| AG-UI | 至少 2 个交互端需要同一 Run 的实时共享状态、Interrupt 和恢复，且轮询 p95 可见延迟超过 2 秒 |
| 标准 OAuth | 任一非家庭 LAN 的第三方 MCP 客户端需要动态接入、资源受众绑定或标准授权发现，即启动评估 |
| PostgreSQL | 需要超过 1 个写实例，或连续两周 `SQLITE_BUSY` 超过写请求的 0.1%，或写锁等待 p95 超过 200ms |
| 外部队列 | 待执行任务持续超过 100、队列等待 p95 超过 60 秒，或单 Worker 无法在约定窗口清空积压 |

达到信号只产生对比实验和迁移决策记录；若现有方案经调优仍满足 SLO，可以不升级。架构升级必须由实际瓶颈触发，而不是由“AI-native”标签触发。

## 10. 风险与反模式

### 10.1 Chat-first，Data-second

把聊天记录当事实会产生陈旧、冲突和不可审计数据。Chat 应是业务对象的视图和入口。

### 10.2 Agent 直接访问数据库

这会绕过字段白名单、归属、事务、审计和迁移约束。Agent 只能调用 Capability。

### 10.3 自动把全部 OpenAPI 转成 Tool

REST 端点数量和粒度通常不适合模型，也会扩大工具面和 Prompt。Tool 应人工精选并面向业务意图。

### 10.4 Prompt 作为权限系统

“不要删除”“只看自己的数据”等 Prompt 不构成安全边界，必须由服务端策略和 Schema 强制。

### 10.5 所有流程 Agent 化

确定性流程使用 Agent 会增加成本、延迟和不可预测性。优先 Workflow，必要环节才由 Agent 判断。

### 10.6 未经使用验证就引入长期 Memory

Memory 可能包含错误推断、隐私和过期偏好。必须有来源、范围、确认、修订和删除机制。

### 10.7 审批只展示自然语言摘要

人类必须看到实际工具、参数、资源、旧值、新值和影响范围；不能只批准 Agent 的概括。

## 11. 调研结论

家庭和中小组织的 AI-native 内部系统，不需要缩小成“聊天机器人”，也不需要膨胀成大型 AI 平台。最稳健的形态是：

> 以模块化领域系统作为事实与规则内核，以 Capability 作为统一动作语言，以 WorkItem/Run/ChangeSet/Approval 作为 Human-Agent 协作骨架，以 MCP 等协议连接外部 Agent，并通过权限、审计、评估和渐进式自治控制风险。

家庭图书管理系统当前已经具备领域内核、入口和权限基础，下一步应补运行与协作对象，而不是重建数据库、替换后端或引入通用 Agent 平台。
