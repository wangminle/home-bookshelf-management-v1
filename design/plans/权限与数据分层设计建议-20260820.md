# 权限、数据分层与用户角色设计建议（下一迭代）

> 2026-08-20 · 基于 v0.3.6 代码现状盘点
> 关联文档：授权矩阵 `agent-authorization-matrix.md`、Agent 规划 `Agent引导入口与能力授权体系规划-20260812.md`
> 本文回答三个问题：**默认（匿名）应该看到什么、登录后应该看到什么、Agent 用什么模式鉴权**，并给出分阶段落地路线。

---

## 0. 现状一句话总结

系统是事实上的 **"owner + 其他人"两档模型**：只有 owner 能登录 Web UI，member/guest 角色字段存在但没有任何代码分支消费它；写路径严格按成员隔离，读路径靠 scope 粗粒度放行；Agent 走 Bearer Token + Grant/Scope（这部分设计良好），渠道头是"可选 HMAC"的明文信任模型。

关键事实（全部有代码依据）：

| 维度 | 现状 | 位置 |
| --- | --- | --- |
| 角色 | `Member.role` 默认 `member`，无枚举约束；只有 `owner` 有差异化行为 | `backend/app/models/member.py:20` |
| Web 登录 | 仅 owner 密码登录；普通成员**无法使用 Web UI**（非 owner web 会话 scope 为空集） | `web_auth.py:210`、`auth_context.py:298` |
| 匿名 | 前端无导航守卫，页面都能打开，但业务 API 全 401——**只见到错误横幅的空壳** | `frontend/src/router/index.ts` |
| 写隔离 | `resolve_body_member`：agent/channel 只能写本人，web owner 可代写 | `auth_context.py:408-440` |
| 读隔离 | **基本没有**：`GET /books/{id}` 返回全部成员子资源，只按 scope 整块裁剪；`GET /stats` 返回全家统计 | `books.py:171-177`、`stats.py:12-18` |
| Agent 授权 | Client/Grant/Token 三表，owner 在 Web UI 直接创建 grant（无申请-审批异步流），默认 30 天 | `services/agent_access.py` |
| 渠道身份 | 不看 role 直接给全量 scope（`auth_context.py:322-325` 死分支）；HMAC 签名可选，未配置则明文头可冒充（BUG-132） | `auth_context.py:108-128` |
| 矩阵落差 | `stats:household` "仅 owner 可授予"未在代码强制；skills 下载声称限流但无实现 | `services/agent_access.py` |

## 1. 默认（匿名）应该看到什么

### 问题

当前匿名体验是最差的一种组合：**页面全开放、数据全 401**。访客打开书架看到的是一个永远转不出来数据的界面和一条错误横幅。同时 `GET /auth/status` 公开暴露"是否已初始化密码"，属于不必要的侦察面。

### 建议：登录墙为默认，"公开书架"为显式开关

家庭场景有两种合理诉求，都应支持，但默认值要明确：

- **默认 = 登录墙**。匿名访问任何页面都重定向到登录/初始化页。理由：书架内容本身就是隐私（读什么书、买什么书、花多少钱），"家人之外的设备连上局域网就能看"不应该是默认行为。实现成本低：前端路由加一个导航守卫调 `/auth/session`，后端无需改动。
- **可选 = 公开书架开关**（`PUBLIC_SHELF_ENABLED`，默认关）。开启后匿名可访问：`GET /books`（仅书目+副本数量，**不含**进度/笔记/购买/统计）和一个只读的书架展示页。典型场景：朋友来家里想翻翻你有哪些书。实现方式是在这些端点上加 `AllowAnonymousShelf` 分支，而不是放开 scope 校验。

### 公开端面收敛

现在公开端点分两类，应区别对待：

| 类别 | 端点 | 处置 |
| --- | --- | --- |
| Agent 发现面 | `/agent/bootstrap.md`、`manifest.json`、`openapi.json`、`skills/*`、`/.well-known/api-catalog`、`/llms.txt` | **保持公开**——这是 Agent 引导契约，内容不含用户数据，是刻意设计 |
| 部署元信息 | `/api/v1/public-health`、`/auth/status` | `public-health` 保持公开（探活需要）；`/auth/status` 考虑只在未初始化时公开，初始化后 401，减少侦察面 |

不要在匿名面里放任何 `frontend_version` 以外的系统信息——`public-health` 目前带版本号可以接受（排障需要），但不要再加 DB 路径、成员数之类的细节。

## 2. 登录后应该看到什么（角色模型落地）

### 问题

`member` 和 `guest` 是死字段。家庭场景的真实需求是：**每个家庭成员都能用自己的身份登录，看全家的书、记自己的进度**。现在只有 owner 一个密码，其他成员要么借 owner 的会话（owner 可代写，但这破坏了数据归属），要么只能用 IM 渠道。

### 建议：三档角色，每档一句话定义

| 角色 | 定义 | 能看什么 | 能写什么 |
| --- | --- | --- | --- |
| **owner** | 系统管理员，管理成员、Agent 授权、绑定关系 | 一切（含全家统计、所有成员数据） | 一切，可代表任何成员操作 |
| **member** | 普通家庭成员 | 家庭共享数据（书目/副本）+ **本人的**进度/笔记/购买/日志 + 本人统计 | 本人的进度/笔记/购买/日志 |
| **guest** | 访客/孩子等受限身份 | 仅家庭共享书目（同"公开书架"内容，但需登录） | 无（或仅本人进度，可配置） |

落地要点：

1. **多成员登录**：`web_sessions` 表已带 `member_id`，机制现成。缺的是成员凭据——建议给每个 member 支持设置独立密码（复用 Argon2id 与失败锁定逻辑），owner 在成员管理页重置。不要上邮箱/验证码，家庭系统保持简单。
2. **读路径补成员隔离**：这是下一迭代最核心的后端改动。`GET /books/{id}` 的子资源（progress/notes/purchases/logs）应按"本人 + owner 可见全部"过滤，而不是按 scope 整块裁剪。scope 控制"能不能看这类数据"，role/成员归属控制"能看谁的数据"，两个维度正交。
3. **`guest` 不要急着做**。如果下一迭代人力有限，先做 owner/member 两档+多成员登录，guest 留字段不实现。先把"member 有意义"做出来比三档齐全更重要。

### 全家统计的归属

`GET /stats` 目前返回全家数据。建议：`stats:read` 只回本人统计（与矩阵文档一致），全家聚合挂 `stats:household`，web 侧仅 owner 可见"家庭"Tab。这同时把矩阵里"stats:household 仅 owner 可授予"的约束在 `POST /agent-access/grants` 里强制补上。

## 3. Agent 用什么模式鉴权

### 结论：Bearer Token + Grant/Scope 已经是正确的主契约，保留并收紧

Client/Grant/Token 三表模型是这套系统里设计最成熟的部分：token 只存 hash、有前缀可识别、级联撤销、过期自动标记。不建议推翻，建议按下面四条收紧：

1. **默认最小 scope**。owner 创建 grant 时前端默认只勾 `books:read`，其余显式勾选；矩阵文档里的"默认建议"列应直接变成 UI 默认值。`books:delete`、`notes:*`、`purchases:read` 加二次确认。
2. **grant 有效期默认缩短到 7 天**，可续期（`POST /grants/{id}/renew`），长期 Agent 用续期而不是 90 天长票。过期自动失效的逻辑已存在，续期是增量。
3. **考虑加"agent 申请 → owner 批准"流**（可选，二期后段）：agent 调 `POST /agent-access/requests` 声明 client 身份和想要的 scope，owner 在 Web UI 批准后生成 grant。这解决"owner 怎么知道该给哪个 agent 什么权限"的引导问题，让 `bookshelf bootstrap` → 申请 → 批准 → 拿 token 成为完整闭环。如果做，approve 动作仍然只产生现有 AgentGrant，数据模型不用变。
4. **明确 CLI/Skills 的契约**：CLI 的 `auth status`、`doctor --authorized` 已以 `BOOKSHELF_TOKEN` 为准，文档已对齐。Agent 主契约就是 Bearer Token，不要再让 Skills 文档暗示渠道头是等价替代。

### 渠道头：从"可选签名"走向"必须签名或禁用"

渠道头是给 IM 网关（lwa 之类）用的，问题在两点：

- `auth_context.py:322-325` 渠道身份不分 role 直接给全量 scope（死分支，owner/非 owner 都一样）；
- 未配置 `CHANNEL_SIGNING_SECRET` 时明文头可冒充任何已绑定成员（BUG-132）。

建议：

1. **渠道身份的 scope 按绑定成员的 role 计算**：绑定 owner → 全 scope（维持现状语义），绑定 member → 去掉 `books:delete`/`members:read`/`stats:household`，绑定 guest → 只读。这样渠道头不再是"全权限后门"。
2. **`CHANNEL_SIGNING_SECRET` 从可选升级为"生产强烈建议"**：`doctor` 在未配置时输出警告；文档把"局域网可信边界"的措辞从"建议配置"改为"凡经反代/网关部署必须配置"。不做强制启用（会破坏纯 loopback 场景），但要在诊断和文档里让它无处遁形。
3. 网关部署时（lwa 场景），签名头应由网关注入而非终端用户持有密钥——这一点已作为 issue 提给 lwa 仓库，本系统只需保证校验逻辑正确。

### Web 会话：保持 Cookie，但会话 scope 应按 role 给

现在 web+owner 短路跳过 scope 检查，web+非 owner 是空集——两头都极端。成员登录落地后，web 会话的 scope 应等于"该 role 的权限集"（owner=ALL，member=共享读+本人写，guest=只读），`require_scope` 对 web 身份也真正生效。这样前端、CLI、Agent 三条路径的权限语义就统一为同一套 scope 语言，便于测试（WBS-6 参数化测试可直接复用）。

## 4. 数据分层（修订矩阵文档 §资源归属规则）

矩阵文档写的规则是对的，代码没跟上。下一迭代以此表为准并改代码：

| 数据 | 归属 | owner | member | guest | agent |
| --- | --- | --- | --- | --- | --- |
| books / copies / tags / custom_fields | 家庭共享 | 读写删 | 读写（删可议） | 读 | 按 scope |
| progress / reading_logs | 成员私有 | 全部 | 本人 | 本人（若允许写） | 绑定成员 |
| notes / attachments | 成员私有，继承父资源 | 全部 | 本人 | 否 | 绑定成员 + scope |
| purchases | 成员私有（财务敏感） | 全部 | 本人 | 否 | 绑定成员 + scope |
| stats | 本人 / 全家两档 | 全家 | 本人 | 本人 | `stats:read`=本人，`stats:household`=全家 |
| members / channel_bindings / agent_access | 系统管理 | 独占 | 否 | 否 | 否（管理端点永远 require_owner） |

两个"可议"点的建议：`books:delete` 对 member 默认不给（误删全家书目代价高）；copies 的 `owner_member_id` 保持元数据语义，不要演变成隔离字段（家里书放谁名下不影响别人读）。

## 5. 分阶段落地路线

按依赖关系排序，每期都可独立交付、可回滚：

**P0（地基，无行为变化）**
1. 修 `auth_context.py:322-325` 死分支，渠道 scope 按绑定成员 role 计算（配测试）。
2. `POST /agent-access/grants` 强制 `stats:household` 仅 owner 可授予。
3. `doctor` 增加 `CHANNEL_SIGNING_SECRET` 未配置警告；文档措辞升级。
4. 矩阵文档标注读路径落差，作为 P1 的验收依据。

**P1（读路径隔离 + 登录墙）**
5. `GET /books/{id}` 子资源按"本人/owner"过滤；`GET /stats` 拆分本人/全家。
6. 前端导航守卫 + 登录页独立化（从 Agent 授权页拆出），匿名一律跳登录。
7. 可选：`PUBLIC_SHELF_ENABLED` 公开书架（开关默认关）。

**P2（多成员登录）**
8. 成员独立密码（设置/重置仅 owner 可操作），`POST /auth/login` 支持任意成员。
9. web 会话 scope 按 role 计算，`require_scope` 对 web 身份生效。
10. grant 默认有效期 7 天 + 续期端点；前端 grant 创建页按矩阵默认建议预勾 scope。

**P3（可选增强）**
11. agent 申请-审批流（`POST /agent-access/requests` + owner 批准 UI）。
12. guest 角色实际启用；`/auth/status` 初始化后收敛。

### 验收口径

每个 P 段完成的标准：授权矩阵文档更新 + WBS-6 参数化测试覆盖新分支 + `doctor` 无新增警告 + 前端对应页面可用。P1 完成前不要在 README 宣称"多成员"。

## 6. 明确不做的事

- **不上 RBAC 框架**（Casbin 之类）：三档角色 + scope 表足够，引入框架只会让 SQLite 家庭项目背上不必要的复杂度。
- **不做 SSO / 第三方登录**：家庭局域网场景，成员密码已够。
- **不给 agent 开放 agent-access 管理端点**：授权管理永远 require_owner，防止被攻陷的 agent 自我提权。
- **不把 `BookCopy.owner_member_id` 变成隔离字段**：归属是元数据，隔离是权限，两者混用会让"全家的书"这个概念破碎。
