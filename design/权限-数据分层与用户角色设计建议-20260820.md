# 家庭图书管理系统：权限、数据分层与用户角色设计建议

> 日期：2026-08-20  
> 状态：下一迭代设计基线  
> 适用范围：Web、REST API、CLI、Agent、渠道接入  
> 核心决策：下一版本采用“局域网匿名可浏览”的 C 模式；登录角色只落地 `owner` 与 `member`；Agent 采用独立服务主体和独立授权，不等同于普通成员。
> 文档优先级：本文记录了本轮确认后的决策；若与 `design/plans/权限与数据分层设计建议-20260820.md` 的旧草稿冲突，以本文为准。

## 0. 结论摘要

下一迭代不应只在现有 Scope 上继续加枚举，而应把权限拆成四个正交维度：

1. **主体身份**：匿名用户、Owner、Member、Agent、渠道调用方；
2. **动作能力**：允许读取、创建、修改、删除、批处理、审批或管理什么；
3. **数据范围**：只访问本人、指定成员、家庭共享数据，还是全家庭聚合数据；
4. **数据可见层级**：数据属于系统公开、局域网共享、家庭业务、成员私有或安全管理层。

统一授权判定建议为：

```text
允许访问 =
  主体已通过相应认证
  AND 动作在主体的能力集合内
  AND 资源位于获批的数据范围内
  AND 字段可见策略允许返回
  AND 风险约束允许本次执行
  AND 授权、会话、网络与系统状态有效
```

核心产品行为：

- 下一版本的匿名局域网用户可以浏览经过字段白名单裁剪的家庭共享书架，但不能访问成员、阅读、笔记、购买、附件原件或管理数据；
- Owner 登录后进入家庭管理视角，拥有人工管理能力和 Agent 审批权；
- Member 登录后进入个人视角，可维护自己的数据，并按家庭策略维护共享书目；
- 不新增 `guest` 角色，匿名只读已经覆盖下一版本的访客需求；
- Agent 是独立服务主体，可获批一些普通 Member 没有的批处理和跨成员自动化能力，但不能自行提权；
- Member 可以发起 Agent 授权申请，只有 Owner 可以批准、修改、续期、暂停和撤销；
- C 模式使用系统策略开启局域网共享；同时预留逐书可见级别，以便未来平滑切换到 B 模式。

## 1. 设计目标与非目标

### 1.1 目标

- 让匿名、登录用户和 Agent 都能明确知道自己可以看到什么、不能做什么；
- 防止“前端隐藏了，但接口仍返回完整数据”的伪权限；
- 支持 Owner、Member 和 Agent 三类已认证主体使用同一套资源与动作语言；
- 允许 Agent 获得高于普通 Member 的自动化能力，同时限制数据范围和高风险动作；
- 使每次授权和重要操作可解释、可撤销、可审计；
- 保留从 C 模式迁移到 B 模式的低成本路径；
- 尽量复用现有 `AuthContext`、Web Session、Agent Client/Grant/Token 与 Scope 基础。

### 1.2 非目标

- 下一迭代不引入 `guest`、儿童、访客管理员等更多角色；
- 不引入 Casbin 等通用策略引擎；
- 不建设互联网级 OAuth 身份提供商、SSO 或社交登录；
- 不允许 Agent 管理 Owner 凭据、查看 Token 明文或自行批准授权；
- 不把“家庭藏书所有人”直接等同于“数据访问控制人”；
- 不在下一迭代实现复杂的逐字段自定义授权界面。

### 1.3 现有基础与主要差距

本文是对现有权限基础的演进建议，不是从零建设。当前代码已经具备：

- `Member.role` 中的 `owner/member` 基础角色字段；
- 统一 `AuthContext`，可识别 Agent Bearer Token、Web Session、渠道身份和匿名请求；
- `require_scope()`、成员归属解析和 CSRF 校验；
- Agent Client、Grant、Token 三层模型，以及 Token 摘要存储、到期和撤销；
- `books:*`、`reading:*`、`notes:*`、`purchases:*`、`stats:*` 等初版 Scope；
- Owner 管理 Agent Client、Grant 和 Token 的 Web 页面。

下一迭代需要解决的主要差距是：

| 维度 | 当前状态 | 目标状态 |
| --- | --- | --- |
| 匿名首页 | 前端路由可打开，但主要业务 API 要求认证，匿名只能看到空页面或错误 | 使用独立 Public Catalog API 提供 C 模式只读书架 |
| Member 登录 | Web 密码登录主要面向 Owner；非 Owner Web 能力没有完整落地 | Owner、Member 均有独立凭据、会话和角色能力集 |
| 数据隔离 | 已有 Scope 和部分成员解析，但读路径仍需系统化落实资源归属过滤 | Scope、归属、层级和字段白名单共同判定 |
| Agent Grant | 现有 Grant 绑定 Member 和 Scope，尚无独立数据范围与风险约束 | Agent 为独立主体，Grant 增加 `data_scope`、约束和版本 |
| Agent 申请 | Owner 可直接创建授权，缺少 Member/Agent 申请与 Owner 决策状态机 | 申请与生效 Grant 分离，Member 最多申请、Owner 唯一批准 |
| 渠道身份 | 兼容路径仍可能给非 Owner 过宽能力，签名存在可选部署情形 | 渠道必须受可信网关签名、角色能力和统一审计约束 |
| C→B 迁移 | 没有逐书目录可见性与匿名模式策略 | `catalog_visibility` 与 `anonymous_catalog_mode` 解耦 |

因此实现时应优先扩展现有 `AuthContext` 和 Agent Grant，而不是另建一套互不相通的鉴权系统。

## 2. 主体模型

### 2.1 匿名局域网用户

匿名用户不是角色，也没有持久身份。其访问能力来自系统的匿名目录策略，而不是 Member 权限。

允许：

- 打开系统首页、共享书架、登录页和 Agent 连接说明；
- 搜索、筛选和查看脱敏书籍详情；
- 读取封面缩略图和公开部署健康状态。

禁止：

- 任何写操作；
- 读取成员名单或推断某本书属于谁；
- 读取阅读进度、日志、笔记、购买、个人评分和附件原件；
- 调用面向自动化的批量 API；
- 通过任意组合查询反推出成员私有数据。

“局域网匿名”不是可靠身份。若系统部署在公网、可信代理配置错误或无法确认来源，应自动降级为登录页和 L0 系统公开层，不能继续开放 L1 书架。

### 2.2 Owner

Owner 是家庭系统管理员，也是唯一的 Agent 授权批准者。

Owner 可以：

- 查看和维护全部家庭业务数据；
- 创建、停用和管理 Member；
- 设置匿名浏览策略和未来的逐书可见策略；
- 查看全家庭统计和安全审计；
- 批准、缩小、拒绝、暂停、续期和撤销 Agent 授权；
- 在必要时代表 Member 执行业务操作，但审计必须记录“操作者”和“数据归属人”两者。

Owner 也不能：

- 读取密码、Web Session、Agent Token 的明文；
- 绕过不可恢复操作的确认与审计；
- 让被撤销或过期的凭据继续生效。

### 2.3 Member

Member 是具有独立登录身份的家庭成员。

Member 默认可以：

- 浏览家庭共享书目和 L2 中允许家庭共享的业务数据；
- 查看和维护自己的阅读进度、日志、笔记、评分和购买记录；
- 查看自己的统计；
- 提交 Agent 授权申请；
- 对涉及自己私有数据的 Agent 申请表达同意或拒绝意见。

Member 默认不能：

- 查看其他成员的私有数据；
- 查看家庭完整购买明细或全量审计；
- 管理成员、角色、认证策略和 Agent Grant；
- 永久删除家庭书目；
- 批准、扩大或续期 Agent 授权。

共享书目由谁维护需要一个系统策略。下一迭代建议默认允许 Member 新增和修正书目、管理自己保管的副本，但不允许删除书目主记录或批量覆盖元数据。

### 2.4 Agent

Agent 是独立服务主体，不属于 `owner/member` 角色枚举，也不是 Member 权限的简单子集。

每个 Agent 至少具有：

- 稳定的 `agent_client_id`；
- 展示名称、客户端类型和可撤销状态；
- 一个或多个由 Owner 批准的 Grant；
- 明确的动作 Scope；
- 明确的数据范围 `data_scope`；
- 有效期、风险约束和审计身份；
- 可选的业务归属成员 `acting_for_member_id`，用于写入阅读、笔记、购买等必须归属个人的数据。

Agent 可以获批普通 Member 没有的能力，例如批量建档、家庭级查重、元数据整理、跨成员聚合统计和受限批处理。但这不等于 Agent 是 Owner，也不允许其管理身份、授权或安全配置。

## 3. 默认看到什么

### 3.1 访问状态矩阵

| 访问状态 | 默认入口 | 默认可见 | 必须隐藏 | 默认操作 |
| --- | --- | --- | --- | --- |
| 匿名局域网用户 | 家庭共享书架 | 书名、作者、封面缩略图、出版社、出版日期、分类、简介、公共标签、脱敏库存状态 | 成员、归属人、精确位置、进度、日志、笔记、评分、购买、原始附件、审计 | 搜索、筛选、查看脱敏详情 |
| 已登录 Member | “我的阅读”与共享书架 | 匿名字段、家庭共享数据、本人进度/日志/笔记/购买/副本、本人统计 | 其他成员私有数据、授权中心管理功能、安全配置、全量审计 | 维护本人数据、按策略维护共享书目、提交 Agent 申请 |
| 已登录 Owner | 家庭管理总览 | 全部业务和管理数据 | 系统不保存或不回显的凭据明文 | 全部人工管理、策略设置、Agent 审批、审计 |
| 未授权 Agent | Agent Bootstrap | 能力说明、Scope 目录、授权申请契约、公开 API 契约 | 家庭业务数据 | 注册客户端、提交申请、查询申请状态 |
| 已授权 Agent | API、CLI 或工具入口 | Grant 允许的资源与字段 | Grant 之外的一切 | 执行获批的自动化任务 |

### 3.2 为什么匿名 Web 与未授权 Agent 不相同

C 模式允许局域网内的人通过 Web 浏览书架，不代表任何自动化客户端都可以匿名遍历数据。原因是自动化抓取速度、可组合查询能力、数据外传风险和审计要求都明显更高。

建议为匿名 Web 书架提供独立的只读 API 和响应模型，例如：

```text
GET /api/v1/public-catalog/books
GET /api/v1/public-catalog/books/{id}
GET /api/v1/public-catalog/covers/{variant}
```

它们只返回 L1 字段白名单，并实施分页、最大页长和基础限流。现有 `/api/v1/books*` 继续要求已认证身份或 Agent Token，避免“为了匿名首页而放开完整业务 API”。

这不是用 User-Agent 区分人和 Agent。系统不信任 User-Agent；边界由不同接口契约、凭据和限流策略建立。

### 3.3 登录后的首页建议

Member 登录后：

- 首屏显示“继续阅读、待读、最近记录、我的借阅或保管副本”；
- 共享书架仍是主导航；
- 成员选择器改为固定显示当前身份，不允许 Member 切换身份；
- 代表他人操作的 UI 完全不对 Member 展示；
- Agent 入口显示“我的申请”，而不是授权管理中心。

Owner 登录后：

- 首屏可切换“我的视角”和“家庭管理视角”；
- 可以查看家庭统计、待处理申请、异常 Agent 活动和最近高风险操作；
- 若 Owner 代表某位 Member 操作，UI 必须明确显示当前业务归属对象，并在完成后恢复 Owner 自己的视角；
- 成员切换不能只改变前端参数，后端仍须验证 Owner 的代操作权限。

## 4. 数据分层与归属

### 4.1 五级数据分层

| 层级 | 名称 | 典型数据 | 默认访问主体 |
| --- | --- | --- | --- |
| L0 | 系统公开层 | 系统名称、登录入口、Agent 能力目录、公开契约、最小健康状态 | 所有人、未授权 Agent |
| L1 | 局域网共享书目层 | 书目基本信息、封面缩略图、公共标签、脱敏库存状态 | 局域网匿名用户、已登录用户；Agent 需只读 Scope |
| L2 | 家庭业务层 | 副本、家庭内部位置、借阅状态、共享自定义字段、非敏感家庭统计 | Owner、Member；Agent 需家庭级数据范围 |
| L3 | 成员私有层 | 阅读进度、日志、个人笔记、评分、购买金额与渠道、个人附件 | 数据本人、Owner；Agent 需数据类型 Scope 和成员范围 |
| L4 | 管理与安全层 | 成员管理、凭据摘要、Agent Grant、审计、安全配置、备份信息 | Owner；Agent 默认禁止 |

### 4.2 资源归属

| 资源 | 归属模型 | 设计说明 |
| --- | --- | --- |
| `Book` | 家庭共享 | 书目主数据不属于某一 Member |
| `BookCopy` | 家庭资产，可有保管人/所有人 | `owner_member_id` 是业务属性，不自动成为访问隔离边界 |
| `ReadingProgress` | Member 私有 | 每个成员独立，禁止 Member 横向读取 |
| `ReadingLog` | Member 私有 | Owner 代写时仍归属目标 Member，并记录真实操作者 |
| `ReadingNote` | Member 私有，可选择未来共享 | 下一版本默认私有，不因书目公开而公开 |
| `PurchaseRecord` | Member 私有、财务敏感 | 金额、渠道、订单信息不得进入匿名或普通家庭聚合响应 |
| 封面缩略图 | L1 | 只提供安全转换后的缩略图，不暴露磁盘路径 |
| 原始封面/电子书/票据/附件 | L3 或更高 | 继承父资源归属与可见级别 |
| 自定义字段 | 显式声明层级 | 新字段默认 `members_only`，不能默认匿名公开 |
| 统计 | 派生数据 | 结果权限不应高于任一必要源数据；匿名只提供预定义脱敏指标 |
| 审计日志 | 系统所有 | Member 可查看本人相关的安全摘要，Owner 查看全局 |

### 4.3 C 模式到 B 模式的兼容设计

逐书可见级别建议为：

```text
catalog_visibility:
  lan_shared    # C：局域网匿名可见
  public        # B：明确允许公开
  members_only  # 仅登录家庭成员
  private       # 指定成员与 Owner
```

系统策略建议为：

```text
anonymous_catalog_mode:
  lan_shared       # 下一版本默认
  explicit_public  # 未来 B
  disabled         # 关闭匿名书架
```

不要在切换模式时批量改写每本书。访问策略根据“记录可见级别 + 系统模式”共同判断：

- `lan_shared` 模式允许读取 `lan_shared` 和 `public`；
- `explicit_public` 模式只允许读取 `public`；
- `disabled` 模式只返回 L0；
- `members_only/private` 始终不能匿名读取。

下一版本若不希望立即给全部存量书写入字段，可以先建立字段和服务器默认值，再用兼容读取规则把旧记录解释为 `lan_shared`。迁移到 B 前必须提供批量预览和批量设置工具。

## 5. 人类用户权限模型

### 5.1 建议的角色能力

| 能力 | Owner | Member |
| --- | --- | --- |
| 浏览 L1/L2 共享书架 | 是 | 是 |
| 维护书目基本信息 | 是 | 是，默认允许单条新增与修正 |
| 删除书目主记录 | 是，需风险确认 | 否 |
| 管理自己的副本 | 是 | 是 |
| 管理他人副本 | 是 | 否 |
| 管理自己的阅读/笔记/购买 | 是 | 是 |
| 查看他人私有数据 | 是 | 否 |
| 查看全家庭统计 | 是 | 否，默认仅本人统计 |
| 管理成员和角色 | 是 | 否 |
| 提交 Agent 授权申请 | 是 | 是 |
| 批准或修改 Agent 授权 | 是 | 否 |
| 查看全量审计 | 是 | 否 |
| 设置匿名和公开策略 | 是 | 否 |

### 5.2 Web 鉴权

- Owner 与 Member 都使用独立凭据登录；
- Web 使用随机不透明 Session Cookie；Cookie 至少设置 `HttpOnly`、`SameSite=Lax/Strict`，HTTPS 下设置 `Secure`；
- 状态变更请求继续实施 CSRF 校验；
- 会话绑定 `member_id`、登录时间、到期时间和撤销状态；
- 修改密码、角色变化、成员停用和安全事件应撤销对应会话；
- 前端路由守卫只负责体验，后端 `AuthContext` 才是安全边界；
- Member 的 Scope 不能是空集，也不能复用 Owner 的全量短路；应由服务器端角色能力表生成。

### 5.3 角色与 Scope 的关系

角色用于人类用户的稳定职责，Scope 用于表达动作能力。两者应共用同一套能力命名，但不必用相同的持久化方式：

```text
Owner role -> 服务器内置 owner 能力集
Member role -> 服务器内置 member 能力集
Agent Grant -> Owner 显式勾选的能力集
```

资源归属检查必须在 Scope 之后继续执行。拥有 `notes:read` 只表示能读笔记这种数据，不表示可以读所有成员的笔记。

## 6. Agent 独立授权模型

### 6.1 为什么 Agent 不是 Member 子集

自动化任务经常需要普通 Member 不具备的能力，例如：

- 批量导入和批量修正元数据；
- 全家庭书目查重与合并候选分析；
- 跨成员生成只含聚合结果的阅读报告；
- 定时维护标签、分类、封面和书架状态；
- 在限制数量和可回滚条件下执行批量写入。

因此不采用“Agent 有效权限不得超过绑定 Member”的简单模型。Agent 的权限来自 Owner 批准的独立 Grant，Member 只决定申请来源或个人数据归属。

### 6.2 Agent 有效权限

```text
Agent 有效权限 =
  Grant.scopes
  INTERSECT 系统允许授予 Agent 的能力
  INTERSECT Grant.data_scope
  INTERSECT 资源数据层级与字段策略
  INTERSECT Grant.constraints
```

Owner 的批准是 Grant 生效的必要条件，但 Owner 身份不会自动附着到 Agent 上。

### 6.3 数据范围 `data_scope`

建议把动作 Scope 与数据范围分开保存。数据范围至少支持：

```text
self(member_id)       # 仅指定成员私有数据
members([id...])      # 指定多个成员
household_shared      # L1/L2 家庭共享数据，不含成员私有数据
household_aggregate   # 可跨成员计算，但只返回合规聚合结果
household_full        # 全家庭明细，高风险，默认不提供
```

典型组合：

| Agent 任务 | 动作 Scope | 数据范围 | 约束 |
| --- | --- | --- | --- |
| 查书 Agent | `catalog:read` | `household_shared` | 只读、分页限流 |
| 入库 Agent | `catalog:read`、`catalog:write`、`copies:write` | `household_shared` + 指定业务归属成员 | 单次最多 N 本 |
| 阅读记录 Agent | `reading:write` | `self(member_id)` | 只能写指定成员 |
| 家庭报告 Agent | `stats:aggregate` | `household_aggregate` | 最小分组阈值、禁止返回明细 |
| 元数据整理 Agent | `catalog:batch_update` | `household_shared` | 先预览、后执行、保留变更集 |
| 私人笔记助手 | `notes:read/write` | `self(member_id)` | 需 Member 同意、Owner 批准 |

### 6.4 Scope 建议

现有 `books:*` 等 Scope 可以兼容保留，但下一迭代建议逐步消除过载：

```text
catalog:read
catalog:write
catalog:delete
catalog:batch_update
copies:read
copies:write
reading:read
reading:write
notes:read
notes:write
purchases:read
purchases:write
stats:self
stats:aggregate
members:read_basic
files:read
```

以下能力不进入普通 Agent Scope，管理 API 始终要求 Owner Web 会话：

```text
members:manage
roles:manage
auth:manage
agent_grants:approve
agent_grants:manage
security:configure
audit:full
backup:manage
```

若为兼容现有实现暂不重命名 Scope，应至少新增动作到资源映射表，并把 `stats:read` 与 `stats:household` 的语义收紧为“本人”和“家庭聚合”，不能继续让一个粗粒度 Scope 返回全部明细。

### 6.5 高风险约束

Agent Grant 除 Scope 和数据范围外，建议增加结构化约束：

- `expires_at`：强制到期；
- `max_items_per_operation`：批处理条数上限；
- `require_preview`：批量修改必须先生成预览或变更集；
- `allow_hard_delete=false`：默认只允许软删除或归档；
- `allowed_member_ids`：允许访问的成员集合；
- `allowed_networks`：可选的来源网络约束；
- `rate_limit_profile`：读取、写入和批处理限流；
- `interactive_confirmation`：高风险调用是否需要一次性确认票据。

`catalog:delete`、跨成员私有明细、原始附件读取和大规模批量覆盖属于高风险授权，应有醒目标识、较短有效期和二次确认。Token 泄露时，风险上限由 Grant 约束决定。

## 7. Agent 申请与审批流程

### 7.1 状态机

```text
draft -> pending_owner_approval -> approved -> active
                         |             |
                         v             v
                      rejected       suspended
                                         |
                                         v
                                      revoked

active -> expired
```

建议简化为：申请记录负责 `pending/rejected/approved`，现有 Grant 负责 `active/suspended/revoked/expired`。批准申请时创建 Grant，而不是让申请本身充当长期权限记录。

### 7.2 谁可以做什么

Member 可以：

- 为自己或家庭共享任务提交申请；
- 查看自己提交申请的状态和 Owner 给出的缩减结果；
- 对访问自己 L3 数据的申请表达同意或撤回同意；
- 请求提前终止与自己数据相关的授权。

Member 不可以：

- 让申请直接生效；
- 修改 Owner 已批准的 Scope、范围、期限和约束；
- 申请身份管理、安全配置或完整审计能力。

Owner 可以：

- 批准、拒绝或缩小申请；
- 选择业务归属成员和数据范围；
- 设置期限与风险约束；
- 暂停、续期、重新签发和撤销；
- 查看 Agent 最近使用情况和异常事件。

### 7.3 Token 交付

- Agent Token 使用随机高熵 Bearer Token，数据库只保存摘要；
- 明文只在签发时显示一次；
- 不放入 URL、二维码查询参数、日志或前端持久存储；
- 令牌与 Agent Client、Grant、到期时间和撤销状态绑定；
- Scope 或数据范围发生变化时，建议旧 Token 立即失效并重新签发；
- 自动化客户端应从操作系统密钥链、Secret Store 或环境注入获取，不写入 Skill 文档或仓库。

### 7.4 Agent 鉴权模式

下一迭代继续以 HTTPS/局域网 HTTP 上的 `Authorization: Bearer <token>` 为主契约。REST、CLI、Skills 以及未来 MCP 都进入统一 `AuthContext`：

```text
Bearer Token
  -> 校验 Token/Client/Grant/期限/撤销
  -> 构建 AgentPrincipal
  -> 校验 Scope
  -> 校验 data_scope
  -> 校验字段策略与风险约束
  -> 执行业务
  -> 写入审计
```

未来若引入 MCP，不应另建一套权限语义；MCP 工具映射到同一 Scope、数据范围和审计模型。OAuth Device Flow 可以作为远程或跨设备场景的后续 Token 获取方式，但不改变资源授权核心。

## 8. 渠道身份与兼容接入

渠道头是网关到系统之间的服务认证方式，不应与 Agent Bearer Token 混用。

建议：

- 渠道签名在生产或反向代理部署中必须启用；
- 签名密钥只由可信网关持有，终端用户不能自行构造身份头；
- 渠道绑定确定业务 Member 身份，能力再按该 Member 角色映射；
- 非 Owner 渠道身份不能获得 Owner 管理能力或全量 Scope；
- 逐步删除“未配置签名即信任渠道头”的兼容路径；
- 渠道请求同样进入 `AuthContext`、归属检查和审计链。

认证优先级不应允许低可信身份覆盖高可信身份。若同一请求同时携带 Bearer、Cookie 和渠道头，建议拒绝冲突凭据或采用明确且可测试的单一优先规则，并在审计中记录冲突。

## 9. API 与后端授权结构

### 9.1 从 Scope 检查升级为策略判定

当前 `require_scope()` 可以保留，但它只是第一层。建议抽象统一判定输入：

```text
authorize(
  principal,
  action,
  resource_type,
  resource_owner_member_id,
  resource_layer,
  requested_fields,
  operation_context,
)
```

输出至少包含：

```text
allowed
denial_reason_code
field_mask
effective_data_scope
audit_risk_level
```

不必引入外部策略引擎。下一迭代可用服务器端常量表和小型策略函数实现，并通过参数化测试锁定行为。

### 9.2 查询时过滤，而不是响应后隐藏

- Member 查询私有资源时，数据库查询必须带 `member_id = principal.member_id`；
- Agent 查询时按 `data_scope` 添加过滤条件；
- Owner 查询全量明细应走显式管理用例；
- 匿名书目使用独立 Select 和独立响应 Schema；
- 嵌套书籍详情中的进度、笔记和购买信息分别按策略查询，不能先加载全部再交给前端隐藏；
- 文件下载必须校验父资源权限，不能只凭文件路径或附件 ID。

### 9.3 字段白名单

L1 匿名书目建议默认返回：

```text
id, title, subtitle, authors, translators,
publisher, publish_date, edition, language,
page_count, category, summary,
cover_thumbnail_url, public_tags,
availability_status
```

默认不返回：

```text
owner_member_id, member_name, exact_location,
file_path, extra, channel_bindings,
reading_progress, reading_logs, reading_notes,
purchase_records, purchase_price, purchase_channel,
raw_attachment_url, operation_log
```

`extra` 和自定义字段不能整体公开；必须逐字段声明层级并进入白名单。

### 9.4 错误语义

| 场景 | 建议状态 | 说明 |
| --- | --- | --- |
| 未提供所需凭据 | `401` | 携带合适的 `WWW-Authenticate` |
| 凭据无效、过期或撤销 | `401` | 不暴露 Token 是否曾存在 |
| 身份有效但缺 Scope/范围 | `403` | 返回稳定错误码，不泄露目标资源存在性 |
| 无权知道目标是否存在 | `404` | 防止枚举其他成员私有资源 |
| 高风险动作缺确认票据 | `409` 或 `428` | 返回可操作的确认流程信息 |
| 超过批量或速率限制 | `429` | 返回重试提示 |

错误正文建议使用稳定机器码，例如 `AUTH_REQUIRED`、`SCOPE_DENIED`、`DATA_SCOPE_DENIED`、`CONFIRMATION_REQUIRED`，而不是让 Agent 解析中文句子。

## 10. 前端信息架构

建议新增或调整以下页面：

1. **匿名共享书架**：只消费 Public Catalog API；顶部提供登录入口；明确“局域网共享视图”。
2. **统一登录页**：Owner/Member 共用，不在 Agent 授权页内嵌 Owner 登录。
3. **Member 首页**：我的进度、待读、日志、笔记、购买和本人统计。
4. **Owner 管理首页**：家庭总览、待处理申请、Agent 异常和安全提醒。
5. **Agent 申请页**：Member 提交并查看自己的申请。
6. **Agent 授权中心**：仅 Owner 可见；展示请求能力、数据范围、期限、约束、最近使用和风险说明。
7. **访问策略页**：仅 Owner 设置 `anonymous_catalog_mode`，并为未来 B 模式预留批量可见性管理。

前端不能根据本地选择的 Member ID 模拟登录身份。当前身份来自 `/auth/session`，成员选择器只在 Owner 明确进入“代操作”模式时出现。

## 11. 审计与安全

### 11.1 审计记录

重要调用至少记录：

- `request_id`；
- 主体类型和主体 ID；
- Agent Client、Grant 与 Token 前缀（不含明文）；
- 实际操作人和业务归属 Member；
- 动作、资源类型、资源 ID；
- 数据范围和有效 Scope；
- 风险等级、结果、拒绝原因码；
- 变更前后摘要或变更集 ID；
- 来源 IP、渠道或客户端类型；
- 时间与耗时。

读取私人笔记、购买信息、原始附件，及所有批量写入、删除、授权变更都应进入高价值审计。

### 11.2 危险动作

- 默认使用软删除或归档；
- 永久删除只允许 Owner 人工执行，或使用极短期、单次确认票据的专用 Agent Grant；
- 批量修改必须支持预览、影响条数、差异摘要和可追踪的变更集；
- 合并书目必须保留来源关系和回滚信息；
- Agent 连续触发拒绝、短时间大批量读取或异常跨成员访问时自动暂停 Grant，并通知 Owner。

### 11.3 C 模式网络边界

C 模式的主要风险是“局域网”判断失误。建议：

- 明确配置可信代理和允许匿名浏览的 CIDR；
- 不无条件信任 `X-Forwarded-For`、`Host` 等客户端可伪造头；
- 不能确认真实客户端地址时按公网处理；
- Public Catalog API 即使在局域网也限流、分页并禁止任意导出；
- 日志不得记录密码、Cookie、Bearer Token、购买订单号和笔记正文。

## 12. 推荐数据模型调整

在现有模型上增量演进，避免一次性重构：

### 12.1 Member 登录

- 将 Owner 专用凭据演进为成员凭据表，或新增 `member_credentials`；
- 一名 Member 对应零或一组可撤销凭据；
- 密码摘要继续使用 Argon2id；
- 保留失败锁定、密码重置和会话撤销能力。

### 12.2 Agent 申请

新增 `agent_access_requests`：

```text
id
agent_client_id
requested_by_member_id
acting_for_member_id nullable
requested_scopes_json
requested_data_scope_json
requested_constraints_json
purpose
status
owner_decision_note
decided_by_member_id nullable
decided_at nullable
created_at / updated_at
```

### 12.3 Agent Grant

在现有 Grant 上增加或规范：

```text
data_scope_json
constraints_json
source_request_id nullable
status: active/suspended/revoked/expired
version
```

Grant 变更建议递增 `version`；Token 绑定签发时版本。版本不匹配则立即失效，避免缩权后旧 Token 继续持有旧权限。

### 12.4 目录可见性

给书目或其家庭目录记录增加 `catalog_visibility`。若未来需要“一本书的不同副本可见性不同”，再把副本级规则作为覆盖项；下一迭代先避免双层可见性带来的复杂度。

## 13. 下一迭代实施计划

### 阶段 0：契约与回归基线

目标：在改变行为前锁定目标权限矩阵。

1. 将本文决策同步到现有 Agent 授权矩阵；
2. 建立“主体 × 动作 × 数据层 × 数据归属”的参数化测试表；
3. 为现有匿名、Owner、Agent、渠道行为补回归测试；
4. 明确旧 Scope 到新动作名称的兼容映射；
5. 不修改现有生产数据。

验收：每个业务端点都有主体、动作、资源层和数据范围定义；不存在“只写了 Scope 名但没有资源规则”的端点。

### 阶段 1：C 模式匿名书架

目标：匿名访问真正可用，同时不开放完整业务 API。

1. 新建 Public Catalog 响应 Schema 和查询服务；
2. 新建只读路由、分页、限流和封面缩略图访问；
3. 增加 `anonymous_catalog_mode` 与可信网络配置；
4. 前端匿名书架改用 Public Catalog API；
5. 对敏感字段做响应契约测试和快照测试。

验收：匿名用户可以完成搜索和浏览；任何匿名响应都不包含成员、位置、阅读、笔记、购买、文件路径或原始附件数据；无法确认局域网来源时自动关闭 L1。

### 阶段 2：Member 独立登录与本人数据隔离

目标：让 `member` 成为真实可用角色。

1. 先写 Owner/Member 登录、锁定、重置、会话撤销的失败测试；
2. 建立成员凭据与统一登录端点；
3. 由服务器角色表生成 Web 能力集；
4. 所有私有资源查询加入 Member 归属过滤；
5. 调整前端会话状态、首页与成员选择器；
6. Owner 代操作显式化并写审计。

验收：Member 不能读取或修改其他成员私有数据；Owner 可在显式代操作状态下处理家庭数据；直接篡改请求中的 `member_id` 无法越权。

### 阶段 3：Agent 申请、独立数据范围和约束

目标：让 Agent 可以获得高于 Member 的受控自动化能力。

1. 先写申请状态机、Owner-only 审批和 Member 不可自批的失败测试；
2. 增加 Access Request 模型与接口；
3. 扩展 Grant 的数据范围、约束和版本；
4. 将 Agent 授权判定从单 Scope 升级为 Scope + Data Scope + Constraint；
5. 增加 Owner 审批 UI 和 Member 申请 UI；
6. Grant 缩权、暂停和撤销后立即使旧 Token 失效；
7. 为批处理增加预览与操作上限。

验收：Agent 可以执行获批的家庭级自动化，但不能越过数据范围、不能自批、不能访问管理与安全层；Member 最多提交申请。

### 阶段 4：为 B 模式预埋逐书可见性

目标：未来从局域网共享切换到明确公开时不重做数据模型。

1. 增加 `catalog_visibility` 和兼容读取规则；
2. Owner 可对单书或批量书目设置可见级别；
3. 提供 C→B 切换预览，列出切换后将消失或继续公开的书；
4. `explicit_public` 模式只返回明确标记为 `public` 的记录；
5. 增加模式切换审计和回滚说明。

验收：三种匿名模式可切换；切换策略不批量篡改书目；私有记录在任何模式下都不会意外公开。

## 14. 测试与验收矩阵

至少覆盖以下场景：

### 匿名

- C 模式可信局域网可以读取 L1；
- 非可信来源、来源不明和 `disabled` 模式不能读取 L1；
- 匿名响应字段白名单严格生效；
- 枚举 ID 不泄露私有记录是否存在；
- 分页、最大页长和限流有效。

### Owner 与 Member

- Owner 和 Member 均可独立登录与登出；
- Member 修改请求中的 `member_id` 不能越权；
- Member 不能查看他人进度、笔记、购买和附件；
- Owner 代操作记录真实操作者和业务归属人；
- 角色变化、密码重置和成员停用后旧会话失效。

### Agent

- 无 Token、错误 Token、过期 Token、撤销 Token 都返回正确 `401`；
- 有 Scope 但数据范围不匹配返回 `403/404`；
- 批处理超过上限或缺预览被拒绝；
- Member 可以申请但不能批准；
- Owner 缩小 Grant 后旧 Token 立即失效；
- `household_aggregate` 只返回允许的聚合结果；
- Agent 永远不能调用成员、凭据、授权审批和安全设置管理接口。

### 渠道与文件

- 伪造渠道头不能冒充 Member；
- 非 Owner 渠道身份没有 Owner 能力；
- 文件下载继承父资源权限；
- 封面缩略图与原始附件使用不同访问策略；
- 冲突凭据按明确规则拒绝或选择，并写审计。

## 15. 需要在实施前锁定但不阻塞本文的参数

以下是实现参数，不改变本设计方向：

- Member 是否默认可以修改所有共享书目的基础元数据，还是只能提交修正；
- Agent Grant 默认有效期采用 7 天、30 天还是按风险等级分档；
- `household_aggregate` 的最小分组人数和隐私阈值；
- 匿名 Public Catalog 的请求频率、最大页长和可信 CIDR；
- 高风险动作使用一次性确认票据，还是只允许 Owner Web 人工执行；
- 存量书目的兼容默认可见级别与切换 B 前的批量确认流程。

建议在下一迭代计划会上把这些参数写成可配置默认值，不要把它们散落为路由里的硬编码判断。

## 16. 最终推荐

下一迭代采用“小型、显式的混合权限模型”：

- 人类用户用 `owner/member` RBAC；
- 私有数据用成员归属隔离；
- Agent 用独立 Client/Grant/Token、动作 Scope、数据范围和风险约束；
- 数据输出受 L0-L4 分层和字段白名单控制；
- C 模式通过专用 Public Catalog API 开放局域网只读书架；
- B 模式通过 `catalog_visibility + anonymous_catalog_mode` 平滑启用；
- 所有路径最终进入统一授权判定和审计模型。

这套模型能支持“Agent 比普通 Member 自动化能力更强，但不拥有全部权限”，也能避免把家庭成员、匿名访客、渠道身份和自动化 Agent 混成同一种信任主体。
